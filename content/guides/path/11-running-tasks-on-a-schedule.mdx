---
title: Running tasks on a schedule
summary: Schedule recurring work with WP-Cron on activation, never twice, clear it on deactivation, and add intervals of your own.
---

Some work shouldn't happen while someone waits for a page: deleting old drafts, syncing with another service, sending
a weekly summary. WordPress's scheduler, **WP-Cron**, runs that work in the background at the times you choose.

## Page loads, not the clock

WP-Cron isn't a clock. A server's own scheduler runs tasks at exact times; WP-Cron can't, because WordPress only runs
when someone requests a page. On each request, WordPress checks (from `init`) whether any event is due. If one is, it
starts a separate background request to `wp-cron.php` to run it, so the visitor's page isn't slowed. On a quiet site
a "daily" event may run hours late, and on a site with no visitors it doesn't run at all.

So schedule work that can tolerate running late. Many hosts turn WP-Cron's page-load trigger off with
`DISABLE_WP_CRON` and call `wp-cron.php` from the server's scheduler instead. Your plugin needs no changes for that.

## Never twice

Always ask <Sym id="function:wp_next_scheduled" /> whether the event is already scheduled before scheduling it.
Without that check, every activation adds another copy, and the task runs once per copy:

<Example id="guides/running-tasks-on-a-schedule/does-not-double-schedule" />

After three activations, the guarded event is scheduled once and the careless one three times. WordPress refuses a
duplicate only for one-off events, and only within ten minutes of an identical one, so never rely on it.

A deactivated plugin's code no longer runs, but its scheduled events stay in the database and keep firing an action

again schedules the event afresh.

## Intervals of your own

WordPress knows four recurrences: `hourly`, `twicedaily`, `daily` and `weekly`. Add your own through the
<Sym id="filter:cron_schedules" /> filter, giving it a prefixed name, its length in seconds and a translated label for
screens that list schedules:

<Example id="guides/running-tasks-on-a-schedule/custom-interval" />

Add the filter on every request, not only on activation, because WordPress needs to know the interval each time it
reschedules the event. <Sym id="function:wp_get_schedule" /> tells you which recurrence an event uses.

The Cron seam isn't ported to SpeedySpec yet, so this guide makes no promise about how scheduled events behave there.
