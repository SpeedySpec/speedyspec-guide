The Query seam holds WordPress's content and the way it is found. Posts of every type, and their meta, comments and
the database layer under them, all live here. So does the machinery that turns a visitor's request into the list of
posts a page shows. This guide explains how those parts connect. For storing your own content type, read
[Storing your own content](/guides/path/storing-your-own-content/) first.

## Posts: one table for all content

Posts, pages, attachments, revisions, menu items and every custom post type are rows in one table, `posts`. The
`post_type` column tells them apart, and `post_status` says where each one is in its life: `draft`, `publish`,
`trash` and so on. In PHP, a row is a <Sym id="class:WP_Post" />, which <Sym id="function:get_post" /> returns by
ID, or `null` when there is none:

## A request becomes the main query

Every front-end request is answered by one query of its own, the **main query**. As the page loads,
<Sym id="function:wp" /> runs <Sym id="class:WP" />'s steps. It matches the address against the rewrite rules,
turns the match into query variables (a post's slug, a category, a page number), and hands them to the main
`WP_Query`. The main query's results then decide which template shows the page.

To change what a page lists, change the main query before it runs, with the <Sym id="action:pre_get_posts" />
action. The query object itself is passed in, so check that it is the main query, and the kind of page you mean, before
changing it:

<Example id="guides/query/pre-get-posts" />

The home page lists three posts, although five exist and the site shows ten by default. The separate query in the
same request was left alone. Never replace the main query with <Sym id="function:query_posts" />. It runs a second
query, discards the first, and confuses everything that reads the main query afterwards.
<Sym id="function:is_main_query" /> says which query is current:

## The Loop

Templates walk a query's posts with **the Loop**: while `have_posts()` says there are more, `the_post()` moves to
the next one and sets it as the global post, so template tags such as `get_the_title()` describe it:

## wpdb: under everything

Every query above ends in <Sym id="class:wpdb" />, WordPress's connection to MySQL. Use it directly only for what no
API covers, such as a custom table, or a query the APIs can't express. Then put every value through `prepare()`
placeholders (`%s` for strings, `%d` for integers, `%i` for table and column names), never into the SQL string:

<Example id="guides/query/wpdb-prepared-read" />

The hostile search found nothing instead of every post. `esc_like()` made the `%` in `100%` a literal character, so it
matched only the title that contains it. Use `$wpdb->posts` and the other table properties rather than writing table
names, because every site has its own table prefix.

The Query seam isn't ported to SpeedySpec yet, so this guide makes no promise about how queries behave there.
