The HTTP seam is how WordPress talks to other servers: update checks, oEmbed, feeds, and every plugin's call to a
service. It also holds the checks on requests coming in from other origins, and whether the site uses HTTPS. This
guide follows a request through its layers. For calling a service from a plugin, read
[Talking to other sites](/guides/path/talking-to-other-sites/) first.

## The layers of a request

A request passes through three layers:

1. **The `wp_remote_` functions** are thin wrappers that only set the method:
   - <Sym id="function:wp_remote_get" />, <Sym id="function:wp_remote_post" /> and <Sym id="function:wp_remote_head" />;
   - <Sym id="function:wp_remote_request" /> for any other method.
2. **<Sym id="class:WP_Http" />** fills in defaults, applies WordPress's filters and checks, and turns the result into
   WordPress's response array.
3. **The Requests library**, bundled under `WpOrg\Requests`, opens the connection with cURL or PHP streams, follows
   redirects and decodes the body.

## Defaults and filters on the way

`WP_Http::request()` merges the arguments with defaults: a 5-second timeout, up to 5 redirects, HTTP/1.0, and a user
agent naming WordPress and the site. Each default has a filter, and <Sym id="filter:http_request_args" /> sees the
whole set:

<Example id="requests/class--WP_Http--request/defaults" />

The example changes each default through its filter, so the values it shows are its own, not WordPress's. Unfiltered,
the HTTP version is `1.0`. <Ev source="wp:wp-includes/class-wp-http.php#L202-L202" hash="87e506aaefe753af98946fc19aba823aea1763b796fc868bcecdaf8884260615"/>

Then come the hooks other code uses to watch or replace requests:

- <Sym id="filter:pre_http_request" /> runs before anything is sent. A value other than `false` becomes the response,
  which is how tests and caching plugins answer requests themselves.
- <Sym id="action:http_api_debug" /> fires with the raw result, for logging.
- <Sym id="filter:http_response" /> can change the final response.

## Limiting where requests go

Two separate checks keep a site from requesting what it shouldn't.

**Safe URLs.** The `wp_safe_remote_` functions set `reject_unsafe_urls`. `WP_Http` then checks the address with
<Sym id="function:wp_http_validate_url" /> before sending it. The URL must be `http` or `https` with no credentials,
and on a usual web port. Its host must not resolve to a loopback, private or reserved address, unless it is the site's
own host. The <Sym id="filter:http_request_host_is_external" /> filter can allow chosen internal hosts.

<Example id="requests/wp_http_validate_url/validate" />

<Example id="requests/wp_safe_remote_get/safe" />

**Blocking external hosts.** A site can set the `WP_HTTP_BLOCK_EXTERNAL` constant in `wp-config.php` to block every
request to other hosts. It then lists the ones it still allows in `WP_ACCESSIBLE_HOSTS`, wildcards included. Requests
to the site itself stay allowed unless <Sym id="filter:block_local_requests" /> says otherwise:

<Example id="requests/class--WP_Http--block_request/block" />

The first check protects against addresses someone supplied. The second is the site owner's choice of what the whole
site may reach. A plugin should work with both.

## Requests coming in: origins

When a browser on another site calls this site's API, it says where it came from in an `Origin` header.
<Sym id="function:get_http_origin" /> reads that header. <Sym id="function:is_allowed_http_origin" /> keeps it only
when it is one of the site's own addresses, or one added through <Sym id="filter:allowed_http_origins" />.
WordPress uses the answer to decide which cross-origin responses the browser may read:
