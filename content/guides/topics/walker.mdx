---
title: Walkers
summary: How the Walker class turns a flat list of items with parents into nested output, and how core walkers use it.
---

The Walkers seam is how WordPress turns a flat list into a tree. Pages, categories, comments and menu items all come
out of the database as a plain list, each item naming its parent. A walker sorts them into levels and calls four
methods as it goes, and those methods write the HTML. Menus, page lists, category lists and comment threads are all
built this way. What trips people up is the depth argument, which counts differently from what you might expect, and
the fact that a walker's methods write into a string passed by reference rather than returning anything.

## The four methods

<Sym id="class:Walker" /> itself writes nothing. Its four output methods are empty, and a walker for a real job
overrides them:

- `start_lvl()` opens a level of children, such as a `<ul>`.
- `start_el()` opens one item.
- `end_el()` closes the item.
- `end_lvl()` closes the level.

<Example id="walker/class--Walker--start_el/base" />

Each method takes `$output` by reference and appends to it. A walker also declares `$db_fields`, which names the
item's ID field and its parent field. The page walkers use `ID` and `post_parent`, the category walkers `term_id` and
`parent`, the comment walker `comment_ID` and `comment_parent`, and the menu walker `db_id` and `menu_item_parent`.
That is the only thing a walker knows about the shape of its items, so the same base class works for all of them.

The examples below use a small walker that writes each item's ID, a `+` when it has children, and brackets around
each level of children.

## Walking a tree

<Sym id="method:Walker::walk" /> takes the items and a maximum depth, and returns the output. It doesn't care what
order the items come in: it first splits them into top-level items (those with an empty parent) and children grouped
by parent, then walks down from each top-level item.

The depth argument is the part to learn. `0` means every level. A positive number is how many levels to show, so `1`
is the top level only. `-1` shows every item flat, at one level, ignoring parents. Anything below `-1` is treated as
invalid and gives an empty string:

<Example id="walker/class--Walker--walk/depths" />

Two edge cases come from real lists. When no item has an empty parent, such as the replies under one comment, the
walker takes the items whose parent is not in the list as the top level:

And with depth `0`, items whose parent is missing from the list aren't dropped. They are written after the tree, at

## What happens per item

`walk()` hands each item to <Sym id="method:Walker::display_element" />. It sets the walker's `has_children`
property, calls `start_el()`, then recurses into the item's children (calling `start_lvl()` before the first and
`end_lvl()` after the last) while the depth allows, and finally calls `end_el()`. It removes the children it has
shown from the list, so they aren't written again as orphans.

<Example id="walker/class--Walker--display_element/one" />

`display_element()` is public, but it is meant to be called by `walk()`. Override it only when you need to change
how children are visited, as the comment walker does.

Any extra arguments you pass to `walk()` are passed on to all four methods. The template functions pass their parsed
arguments this way, which is why `start_el()` in the core walkers reads options such as `item_spacing` or
`show_count` from `$args`.

## Writing your own

Most changes need a filter, not a walker. Adding a class, an attribute or an icon to a menu item is one filter on the
default walker, and it keeps working with every theme. Write a walker when the structure itself has to change.

When you do, extend the closest core walker rather than `Walker`, and override only the methods you need. Keep the
method signatures exactly as the parent declares them, including `&$output`. Escape what you write: the core walkers
do, and a custom `start_el()` that echoes a title or URL raw is a cross-site scripting hole. Pass an instance through
the template function's `walker` argument.

The Walkers seam isn't ported to SpeedySpec yet, so this guide makes no promise about how walkers behave there.
