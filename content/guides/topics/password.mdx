---
title: Passwords and crypto
summary: How WordPress hashes and checks passwords, how old hashes are upgraded, and how application passwords are made, stored and checked.
---

The Passwords and crypto seam holds two classes: <Sym id="class:PasswordHash" />, the phpass library WordPress used
to hash passwords before 6.8, and <Sym id="class:WP_Application_Passwords" />, which manages the separate passwords
people give to apps and scripts. The functions plugins call, such as `wp_hash_password()`, live in `pluggable.php`,
but they only make sense next to these classes, so this guide covers them too. What trips people up is that a site
holds hashes of several ages at once, and WordPress must accept all of them while it quietly replaces the old ones.
For how a login turns into a user, read the [Identity](/guides/topics/identity/) guide.

## Hashing a password

<Sym id="function:wp_hash_password" /> turns a password into a hash for storing. Since 6.8 it uses bcrypt, through
PHP's `password_hash()`. bcrypt only reads the first 72 bytes of its input, so WordPress first runs the password
through HMAC-SHA384 and hashes that instead. The result starts with `$wp`, so WordPress can tell its own bcrypt
hashes from plain ones:

<Example id="support/wp_hash_password/hash" />

The `wp_hash_password_algorithm` and `wp_hash_password_options` filters can choose another algorithm, such as
Argon2, or a higher cost. The pre-hash only applies to bcrypt. A password longer than 4096 bytes isn't hashed at all:
the function returns `*`, which no password matches.

<Sym id="function:wp_check_password" /> checks a password against a stored hash. It looks at the hash to decide how:
a `$wp` hash goes through the HMAC and `password_verify()`, a `$P$` hash goes to phpass, and a hash of 32 characters
or fewer is compared as MD5. Other hashes go to `password_verify()` directly. The `check_password` filter gets the
final answer:

<Example id="support/wp_check_password/check" />

Both functions are pluggable, so a plugin can replace them. Few should. If you do, keep the same rule: never compare
hashes with `==`, and accept every format already stored on the site, or people get locked out.

## Upgrading old hashes

A hash records how it was made, so WordPress can ask whether it is out of date.
<Sym id="function:wp_password_needs_rehash" /> says yes when the hash isn't from the current algorithm and options.
With the default bcrypt, an MD5 or phpass hash always needs one:

<Example id="support/wp_password_needs_rehash/rehash" />

The upgrade happens at login. When the username and password check succeeds and the stored hash needs a rehash,
WordPress calls <Sym id="function:wp_set_password" /> with the password the person just typed. That is the only
moment the plain password is known, so it is the only moment the hash can be replaced. `wp_set_password()` writes
the new hash straight to the users table, clears the password reset key and the user's cache, and fires the
`wp_set_password` action:

<Example id="support/wp_set_password/set" />

Because it skips `wp_update_user()` and its checks, call `wp_set_password()` only when you mean to replace a password
outright, after checking the current user may do so.

## The phpass library

<Sym id="class:PasswordHash" /> is still bundled, because hashes it made are still stored on older sites, and
`wp_check_password()` hands them to it. In portable mode it makes `$P$` hashes: a salt, then MD5 run over and over,
two to the power of the cost given. It is far weaker than bcrypt. New code should never create these hashes:

<Example id="password/class--PasswordHash--HashPassword/portable" />

Not portable, it uses PHP's bcrypt and makes `$2a$` hashes. Like `wp_hash_password()`, it refuses passwords longer
than 4096 bytes:

<Example id="password/class--PasswordHash--gensalt_blowfish/blowfish" />

It writes salts and hashes in its own base64 alphabet. `crypt_private()` gives `*0` or `*1` for a setting it doesn't
understand, so a bad hash can never match:

<Example id="password/class--PasswordHash--encode64/encode" />

The global `$wp_hasher` used to hold a `PasswordHash`. If a plugin still sets it, `wp_hash_password()` and
`wp_check_password()` use it instead of bcrypt. Don't set it in new code.

## Fast hashes for tokens

Passwords are short and guessable, so their hashes are slow on purpose. Random tokens and keys are long and
unguessable, so a slow hash only wastes time. For those, WordPress has <Sym id="function:wp_fast_hash" />, a BLAKE2b
hash marked `$generic$`:

<Example id="support/wp_fast_hash/fast" />

<Sym id="function:wp_verify_fast_hash" /> checks one, in constant time. A hash without the `$generic$` marker is
treated as an old phpass hash:

<Example id="support/wp_verify_fast_hash/verify" />

Never use `wp_fast_hash()` for a password a person chose. Use it for secrets your code generates.

## Application passwords

An application password lets an app or script authenticate to the REST API or XML-RPC as a user, without the user's
real password. Each one can be revoked on its own. They are kept, hashed, in the user's `_application_passwords`
meta.

`WP_Application_Passwords::create_new_application_password()` makes a 24-character password of letters and digits,
gives it back in plain text once, and stores only its `wp_fast_hash()`. It needs a name. Creating the first one also
marks the site as using application passwords, and the user is emailed:

<Example id="password/class--WP_Application_Passwords--create_new_application_password/create" />

Show the plain password once, right away, and never store it. There is no way to read it back later.

Each password has a UUID. Update, record use of and delete it by that UUID. Each change fires its own action:
<Sym id="action:wp_create_application_password" />, <Sym id="action:wp_update_application_password" /> and
<Sym id="action:wp_delete_application_password" />. An unknown UUID gives a `WP_Error`:

<Example id="password/class--WP_Application_Passwords--update_application_password/manage" />

`check_password()` checks a password against a stored hash. Hashes made before 6.8 don't have the `$generic$`
marker, so they go through `wp_check_password()`. `chunk_password()` splits a password into groups of four, for
showing it to a person:

## When application passwords work

Application passwords are only available when <Sym id="function:wp_is_application_passwords_available" /> says so.
By default that means the site uses HTTPS or its environment type is `local`, because the password travels in a
header on every request. The `wp_is_application_passwords_available` filter can turn them on or off:

<Example id="identity/wp_is_application_passwords_available/available" />

When a REST or XML-RPC request arrives with a Basic `Authorization` header,
<Sym id="function:wp_validate_application_password" /> runs on `determine_current_user` and looks for a matching
application password. Outside those requests it passes the user it was given straight on:

<Example id="identity/wp_validate_application_password/validate" />

Don't turn them on over plain HTTP in production. Anyone who can read the traffic can read the password.

The Passwords and crypto seam isn't ported to SpeedySpec yet, so this guide makes no promise about how passwords
behave there, with one exception decided in advance. SpeedySpec won't verify phpass (`$P$` and `$H$`) or MD5
hashes. People whose passwords are still stored that way will need to reset them with "Lost your password?", and
values hashed with phpass before WordPress 6.8, such as old reset keys, will stop working.
