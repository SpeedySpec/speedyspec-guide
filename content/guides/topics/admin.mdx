title: Admin

The Admin seam is everything under `wp-admin/`: the screens themselves and the roughly 700 functions they load. Most of
it serves WordPress's own screens. This guide covers the parts plugin authors use: menu pages, the Settings API,
notices, meta boxes, list tables, screen options, and the two entry points for handling forms and Ajax. What trips
people up is timing. These functions exist only once the admin has loaded, and each has a hook it belongs on. For a
first settings screen, read [Adding a settings page](/guides/path/adding-a-settings-page/); for the dashboard, read
[Adding a dashboard widget](/guides/path/adding-a-dashboard-widget/).

## The order of an admin request

`wp-admin/admin.php` loads WordPress and the admin's include files, then works through a fixed order. It builds the
menu and fires <Sym id="action:admin_menu" />. Then it fires <Sym id="action:admin_init" />, works out the current
screen and fires `current_screen`. For a plugin's page it fires `load-{$page_hook}`, then prints the header, with
<Sym id="action:admin_enqueue_scripts" /> and <Sym id="action:admin_notices" /> on the way, and finally calls the page's
own callback. Note that `admin_menu` comes **before** `admin_init`.

## The Settings API

For a page that saves options, the Settings API builds the form and checks the submission. Register the option with
<Sym id="function:register_setting" /> (from the Options seam) and a sanitize callback, then describe the form on
`admin_init`. <Sym id="function:add_settings_section" /> adds a titled section to a page, and
<Sym id="function:add_settings_field" /> adds a field to a section, each with a callback that prints it. On the page,
<Sym id="function:do_settings_sections" /> prints them all:

<Example id="admin/do_settings_sections/example" />

The form posts to `options.php`. Inside it, <Sym id="function:settings_fields" /> prints the hidden fields that name the
option group and carry its nonce, which `options.php` checks before it saves anything:

<Example id="admin/settings_fields/example" />

Only options registered to the group are saved, so a field for an unregistered option is silently ignored.

users it concerns: check `get_current_screen()` and a capability first, and escape the message.

## Screen options

The Screen Options tab holds per-user choices such as items per page. Add one with
<Sym id="function:add_screen_option" />, on your page's `load-` hook:

<Example id="admin/add_screen_option/example" />

When a user submits the tab, `set_screen_options()` checks its nonce, saves the value as user meta and redirects back.
WordPress saves its own options without help. For yours, it saves the value only if
<Sym id="filter:set_screen_option_{$option}" /> returns it, so hook that filter with a function that returns the
cleaned value. Without it, the choice is quietly dropped. `set_screen_options()` runs early, before `admin_menu`, so add
the filter when your plugin loads, not on your page's `load-` hook.

The old `screen_options()` function is deprecated since 3.3.0; the screen's `render_per_page_options()` method replaces
it.

## List tables

The admin's tables of posts, users and comments are subclasses of <Sym id="class:WP_List_Table" />, which the admin
loads on every admin screen. Its docblock in this version does not mark it private, but it was written for WordPress's
own screens, so test a subclass against each new release. A subclass must at least define `get_columns()` and
`prepare_items()`; the base class stops with an error if either is missing. It prints a cell with `column_default()` or
a `column_{$name}()` method, and the whole table with `display()`. Escape every cell.

WordPress's own tables are made by <Sym id="function:_get_list_table" />, which is private: it only knows WordPress's
classes. To change those tables, use their filters rather than the classes:

<Example id="admin/_get_list_table/example" />

Columns come from the `manage_{$screen->id}_columns` filter, which is where a plugin adds one to an existing table:

<Example id="admin/get_column_headers/example" />

<Sym id="function:get_hidden_columns" /> gives the columns each user hid, stored per screen as a user option.

## Handling forms and Ajax

A plugin's own forms post to `admin-post.php` with a field named `action`. WordPress then fires
<Sym id="action:admin_post_{$action}" /> for logged-in users and `admin_post_nopriv_{$action}` for visitors, and answers
400 when nothing is hooked. The handler checks a nonce and a capability, does the work, redirects with
`wp_safe_redirect()` and exits.

Ajax requests go to `admin-ajax.php` in the same way: <Sym id="action:wp_ajax_{$action}" /> for logged-in users,
`wp_ajax_nopriv_{$action}` for visitors. A handler checks its nonce with `check_ajax_referer()` and a capability, and
ends with `wp_send_json_success()` or `wp_send_json_error()`. WordPress's own handlers follow the same pattern, such as
the one that remembers which boxes a user collapsed:

<Example id="admin/wp_ajax_closed_postboxes/example" />

Hooking `nopriv` makes the action open to anyone. Only do it for work a visitor may do, and never let it change data on
the strength of a nonce alone. For a new API, a REST route is often the better choice.
[Admin notices and Ajax](/guides/path/admin-notices-and-ajax/) puts a notice and an Ajax handler together.
