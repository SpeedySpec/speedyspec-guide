## Differences

- **`site` meta on a single site** maps to `wp_sitemeta`, where WordPress's `_get_meta_table( 'site' )` is false and every meta function given `'site'` fails. On SpeedySpec those functions read or write `wp_sitemeta`: `add_metadata()`, `update_metadata()`, `delete_metadata()`, `get_metadata()`, `get_metadata_raw()`, `metadata_exists()`, the three `*_by_mid()` functions and `update_meta_cache()`. The options seam's network code relies on that table name. <Ev source="ss:crates/speedyspec-wp-meta-sql/src/repository.rs#L409-L412" hash="29a136921eb9b816414883ee9065616182ae0208fb47091146cd9f6e5179566a"/>
- **Objects in meta values** reach hooks as copies made by `serialize()` and `unserialize()`, not as the object the caller passed: in `add_metadata()`, `update_metadata()`, `delete_metadata()`, `update_metadata_by_mid()`, `sanitize_meta()` and `filter_default_metadata()`. <Ev source="ss:crates/speedyspec-wp-meta-php/src/codec.rs#L3-L13" hash="9ad5f408eef9d41cda7cf40d1d761ed16a0c161faacd2753523b3e445c4bb0b4"/>
- **`get_metadata_default()`** passes `default_{$meta_type}_metadata` the object id after `absint()`, where WordPress passes it as given. <Ev source="ss:crates/speedyspec-wp-meta-php/src/native.rs#L276-L281" hash="57109ac53d4d08266c2915a0d1d308063d547024e2afa260b60cd19feb6762c0"/>

Each is on the pages of the functions it touches.

## Still WordPress's PHP

`get_meta_sql()`, which builds a `WP_Meta_Query`. Its port comes with `WP_Query`'s. The rest of `meta.php` loads beside the native functions. <Ev source="ss:crates/speedyspec-wp-meta-php/src/release.rs#L9-L10" hash="7abfe15425f59212735070a8107ed756ba290bc96c8ca900ea0a3d5a8262bb99"/>

The ports that ask other seams (a post's type, a term's taxonomy, whether a site exists, `post_type_supports()`, the REST schema check, `wp_installing()`) call WordPress's PHP until those seams are wired. See the architecture page.
