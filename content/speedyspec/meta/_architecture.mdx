## The crates

Each declares `seam = "meta"` and its role in `[package.metadata.speedyspec]`.

- **`speedyspec-wp-meta-contracts`** (contracts, in speedyspec-platform, taken from crates.io): the values `MetaType`, `MetaKey`, `ObjectId`, `MetaId` and `SerializedValue`, the `Meta` entity, `MetaError` and `MetadataError`, the `Metadata` contract, the `MetaKeys` read port, the outbound ports, and the repository conformance suites behind the `conformance` feature. It depends on the hooks and object cache contracts and on `speedyspec-php-serialize` only. <Ev source="ss:crates/speedyspec-wp-meta-contracts/src/lib.rs#L16-L24" hash="b9abd96cecca5203ce70d93cc5cedf45e517a84805d6f55174a6c29e295629a4"/> <Ev source="ss:crates/speedyspec-wp-meta-contracts/Cargo.toml#L24-L27" hash="e8956526b710610e19c2b4ef2d3d09f1259c889ecc2e29d1884031a7cf8e0c3a"/>
- **`speedyspec-wp-meta`** (implementation): `MetadataApi`, one use case per `meta.php` function, over the ports; the metadata messages and their handlers; `LazyLoader`; and phase 1's rules (protected keys, `register_meta()`'s two halves, `MetaKeyRegistry`). <Ev source="ss:crates/speedyspec-wp-meta/src/lib.rs#L1-L8" hash="4b3f1ed5aae616f6f16241374b1a734bf0bf38700db2c9800ef4ff4c794a1f87"/>
- **`speedyspec-wp-meta-sql`** (adapter): `SqlMetaRepository` and `SqlMetaRepositories`, the meta tables through the `Wpdb` port, and `MetaMapper`. <Ev source="ss:crates/speedyspec-wp-meta-sql/src/repository.rs#L1-L8" hash="704ec7e2ccc7adff17cb2055ec40423e07f95bdca4c06d3298793baaaa0f86eb"/>
- **`speedyspec-wp-meta-memory`** (adapter): one table in memory, for tests and callers with no database. <Ev source="ss:crates/speedyspec-wp-meta-memory/src/lib.rs#L1-L4" hash="ceb86a45f686f9390845660fb79b1641cd2410e649c8b0872a44c1a371ea5bd6"/>
- **`speedyspec-wp-meta-php`** (adapter): `MetaArea`, which declares the 23 ported functions and `WP_Metadata_Lazyloader` in PHP over the native API, and the PHP adapters of the outbound ports. <Ev source="ss:crates/speedyspec-wp-meta-php/src/lib.rs#L1-L16" hash="1e587bfd98c1e8c4e92bf03e61785df8bfb11061b2cf09cad57311eb56c46d84"/>

## The contracts

- **`Metadata`**: the metadata API as one trait, a method per function: `add`, `update`, `delete`, `get`, `get_raw`, `get_default`, `exists`, `get_by_mid`, `update_by_mid`, `delete_by_mid` and `update_cache`. Every method takes the meta type first; values are PHP values, which the implementation serializes as `maybe_serialize()` does. <Ev source="ss:crates/speedyspec-wp-meta-contracts/src/metadata.rs#L23-L27" hash="f27d03b629fd063f76a09bfe0efd8d312d0d5adc5fd00b6a7408b119040ba611"/> `update` answers `UpdateOutcome`: `Updated`, `Added(MetaId)`, `Unchanged` or `Failed`, the four things `update_metadata()` can mean. <Ev source="ss:crates/speedyspec-wp-meta-contracts/src/metadata.rs#L10-L21" hash="b6a56b6a0f1208ff24da794d45bd486270c483b0893fb863871949b0cccec338"/>
- **`MetaRepository`**: one meta table, one method per `$wpdb` call `meta.php` makes, so query counts match WordPress's. A failure `$wpdb` hides is `Ok` with the empty answer. <Ev source="ss:crates/speedyspec-wp-meta-contracts/src/ports.rs#L1-L4" hash="8b609d351116374d62cd52e1173e69c251f4ce07a1d9df403b472237505c78ad"/> **`MetaRepositories`** is `_get_meta_table()` as a factory: the shared repository for a type, or `None` when the type has no table. <Ev source="ss:crates/speedyspec-wp-meta-contracts/src/ports.rs#L68-L72" hash="293bcc5276b730f7be2f109fb0a0ccde17ff00f787100fb978063bf0c91f3ccb"/>
- **`MetaKeys`**: the read port over `$wp_meta_keys`, `keys()` for `get_registered_meta_keys()` and `find()` for one key. <Ev source="ss:crates/speedyspec-wp-meta-contracts/src/keys.rs#L34-L41" hash="ccd28d2af497404b8ac81444cfa3641d1f26e15beb1faa83aad70d10ef72ce33"/> `speedyspec-wp-meta` extends it as `MetaKeyIndex`, which also lists a type's subtypes, because `filter_default_metadata()` walks them; the method moves into the contracts in their next release. <Ev source="ss:crates/speedyspec-wp-meta/src/registry.rs#L92-L95" hash="11876575c31bad6ae100b699859c4c31052d38540cdff6d4c21906915dda716d"/>
- **The outbound ports**: what `meta.php` asks of other seams. `ObjectSubtypes` (`get_object_subtype()`'s switch), `RevisionSupport` (`post_type_supports()`), `DefaultSchemaCheck` (`rest_validate_value_from_schema()`), `Callables` (`is_callable()`), `ProtectedMeta` (`is_protected_meta()`'s rule) and `Installing` (`wp_installing()`). <Ev source="ss:crates/speedyspec-wp-meta-contracts/src/ports.rs#L74-L103" hash="1d0df1b44c74a0cf0ec2f1e7921686df70f3a23dc4ab23992f1673e31064c840"/>

## MetadataApi and the handler keys

`MetadataApi::new(MetaDeps)` builds the use cases from their ports: the Hook API, the request's object cache, the repositories, the registered keys, the subtypes, the unfiltered protection rule and the installing check. <Ev source="ss:crates/speedyspec-wp-meta/src/api.rs#L42-L52" hash="853c28c79e1133a102c0051abd770d7feb216c3de054b6d6a88de239922c27e9"/> It implements `Metadata`. Where WordPress returns a short-circuit filter's answer unchanged, the contract's narrower types keep what they can carry; the inherent methods and the messages keep the whole answer. <Ev source="ss:crates/speedyspec-wp-meta/src/api.rs#L288-L291" hash="eab4c650b1c886c95e29989c5ea2fa9098931039d184ee83a6c59190d5bf23e5"/>

Every function is a message on the buses, handled by `MetadataApi` and bound in the container at `SpeedySpec\WpMeta\<Message>Handler`: <Ev source="ss:crates/speedyspec-wp-meta/src/messages.rs#L23-L34" hash="829aca0136fba37c11357ae609ff53394ae11370050c79dfbef004172fea25c3"/> <Ev source="ss:crates/speedyspec-wp-meta/src/messages.rs#L99-L105" hash="1dd5a09121a39248cd1c93ecbc38866eb0bb35231383400b8815a8a764b72913"/> <Ev test="speedyspec-wp-meta-tests::use_cases::handlers_are_bound"/>

| Kind | Messages |
|------|----------|
| Commands | `AddMetadata`, `UpdateMetadata`, `DeleteMetadata`, `UpdateMetadataByMid`, `DeleteMetadataByMid`, `UpdateMetaCache` |
| Queries | `GetMetadata`, `GetMetadataRaw`, `GetMetadataDefault`, `MetadataExists`, `GetMetadataByMid`, `SanitizeMeta`, `IsProtectedMeta`, `GetObjectSubtype`, `FilterDefaultMetadata` |

The PHP functions reach the use cases through these handlers, each resolved once from the container, so a handler bound in their place takes the call. <Ev source="ss:crates/speedyspec-wp-meta-php/src/native.rs#L1-L6" hash="108df10412918d0bde61be6efe3fb382e8e5d4c7724aa527d52464e3da08a7e2"/> `register_meta()` and the other registry functions work on `$wp_meta_keys` itself, through phase 1's rules and `MetadataApi::resolve_registration`, so a callback's identity is kept. <Ev source="ss:crates/speedyspec-wp-meta/src/api.rs#L107-L118" hash="92bc7a18409bb9a68b592f1e86cc52c0502205a4268ee5b7572f2a75625670ce"/>

`LazyLoader` is `WP_Metadata_Lazyloader`'s queue and loading. Adding and removing the `get_{$type}_metadata` callback stays PHP's job, because the callback is a PHP callable. <Ev source="ss:crates/speedyspec-wp-meta/src/lazy.rs#L1-L6" hash="3fe669f50a81792237b191462b45267e618faabca9f13dfa2198916d927be270"/> <Ev test="speedyspec-wp-meta-tests::lazy::queue_then_one_get_loads_all"/>

## The adapters

- **SQL**: `SqlMetaRepository` sends `meta.php`'s own statements through `wpdb`: reads through `prepare` with WordPress's templates, so the `query` filter sees WordPress's text, and writes through `insert`, `update` and `delete`, so charset stripping and the changed-rows count are `wpdb`'s. The table is read from `wpdb` on every call, so `switch_to_blog()` is followed. <Ev source="ss:crates/speedyspec-wp-meta-sql/src/repository.rs#L1-L8" hash="704ec7e2ccc7adff17cb2055ec40423e07f95bdca4c06d3298793baaaa0f86eb"/> It passes the repository suite on SQLite and MySQL. <Ev test="speedyspec-wp-meta-sql::engines::suite_on_sqlite"/> <Ev test="speedyspec-wp-meta-sql::engines::suite_on_mysql"/> Two differences are known: `update_meta_cache()`'s query selects the meta id too, and on a single site the `site` type has a table. <Ev source="ss:crates/speedyspec-wp-meta-sql/src/repository.rs#L324-L326" hash="fb932a37a03b40268c4645836488874618bd4145070eb1d1ef45eb2037765e49"/> <Ev source="ss:crates/speedyspec-wp-db/src/contract.rs#L9-L18" hash="50cf694ed9e009bbef4e2f33680c81b4a234952e78670d7e3773a87cce54931d"/>
- **Memory**: `MemoryMetaRepository` and `MemoryMetaRepositories` pass the same suite, and the opt-in binary-safe one. <Ev test="speedyspec-wp-meta-memory::conformance::memory_repository_passes_the_suite"/> <Ev test="speedyspec-wp-meta-memory::conformance::memory_repository_passes_the_binary_safe_suite"/>
- **PHP**: `PhpMetaKeys` reads `$wp_meta_keys` live; `PhpObjectSubtypes`, `PhpSites`, `PhpRevisionSupport`, `PhpDefaultSchemaCheck`, `PhpCallables` and `PhpInstalling` call WordPress's functions until the seams that own posts, terms, comments, users and sites bind Rust ones. `PhpValueHooks` makes the use cases' values PHP values on the way into a hook, and `PhpTableNames` reads a table a plugin declares as a dynamic property of `$wpdb`. <Ev source="ss:crates/speedyspec-wp-meta-php/src/lib.rs#L98-L115" hash="b6bf18bfede06296cd5e5b65bf4b95dbb1b6a84102d99d519a78aa3a40494975"/> <Ev source="ss:crates/speedyspec-wp-meta-php/src/adapters.rs#L293-L295" hash="49e878484990fa313a63e295273f00abee5b6e674103c6acc6d9057cb79adcde"/>

## Replacing the storage

The repositories are a port in the container, at `SpeedySpec\WpMeta\MetaRepositories`. The SQL tables are its default binding, and the use cases resolve it on every call, so a binding made for the request applies. <Ev source="ss:crates/speedyspec-wp-meta-php/src/lib.rs#L92-L97" hash="0a9de7f2ccc78a3d5121d1d5417f2169931cdc855f0e855d6125b8fac3fd623a"/> <Ev source="ss:crates/speedyspec-wp-meta-php/src/adapters.rs#L385-L391" hash="c272735084d297d2a8d071fa0ecf7f3f829f56ec4e7a724731a7214689a04bf9"/>

- **From Rust:** implement `MetaRepository` and `MetaRepositories`, run the contracts' `meta_repository_suite` against them, and bind them at that key.
- **From PHP:** implement the `SpeedySpec\WpMeta\MetaRepositories` and `SpeedySpec\WpMeta\MetaRepository` interfaces, which the area declares at the start of every request, and bind an object at the same key. <Ev source="ss:crates/speedyspec-wp-meta-php/src/twins.rs#L1-L7" hash="0befe2342227ccfd057a9f4a903c3902f7736cfd9f8a6733b29bc3f5449aabba"/> The worker registers the port, so the binding reaches Rust. <Ev source="ss:crates/speedyspec-php-runtime/src/worker.rs#L312-L313" hash="62dc6b19f9da2a5b3abfd965bbe5305bbcc5b929f8b8999e8eaac42c93212b6a"/> A binding lasts for its request, and a binding that throws reaches the caller as a `ContainerException`; nothing falls back to SQL. <Ev source="ss:crates/speedyspec-wp-meta-php/tests/replacement.rs#L40-L70" hash="d20edf695e5b3db09406c8a2fab2d1a1008a663cf0671dac54b7027a3c1cc10b"/>

## A runtime feature calling the API

A Rust feature that needs a post's meta asks `Metadata`, which `MetaArea::api()` gives: the same use case PHP's `get_metadata()` runs, with the `get_post_metadata` filter, the object cache and the registered default. <Ev source="ss:crates/speedyspec-wp-meta-php/src/lib.rs#L129-L132" hash="d6ac8763df0722f365018a61f238dfab7531eebece3089f3174512ed7b85c033"/>

```rust
use speedyspec_php_serialize::PhpValue;
use speedyspec_wp_meta_contracts::{MetaKey, MetaType, Metadata, MetadataError, ObjectId};

/// A post's featured image id, as `get_post_meta( $post_id, '_thumbnail_id', true )` reads it.
fn thumbnail_id(meta: &dyn Metadata, post: u64) -> Result<Option<u64>, MetadataError> {
    let Some(post_type) = MetaType::new("post") else {
        return Ok(None);
    };
    let key = MetaKey::from("_thumbnail_id");
    // `single`: the first value, or '' when the post has none.
    let value = meta.get(&post_type, ObjectId(post), Some(&key), true)?;
    Ok(match value {
        PhpValue::Int(id) => u64::try_from(id).ok(),
        PhpValue::Str(bytes) => std::str::from_utf8(&bytes).ok().and_then(|s| s.parse().ok()),
        _ => None,
    })
}
```

To let PHP rebind the use case, send the message instead: `GetMetadata` through the query bus reaches whatever handler is bound at `SpeedySpec\WpMeta\GetMetadataHandler`.
