## Behaviour

The PHP twin of the `PasswordChecker` port, which answers `wp_check_password()`. Its one method, `check( $password, $hash, $user_id )`, answers whether the password matches the hash; `$user_id` is passed as the caller gave it. `#[php_port]` declares it at the start of every request from the Rust trait, so the two can't drift. <Ev source="ss:crates/speedyspec-wp-password-php/src/twins.rs#L16-L20" hash="45f9203babd92d82922f7e1c588138eda9c1a86daa7caab1a1c82b7cefc2355e"/>

## Override

Where WordPress lets a plugin declare `wp_check_password()` first, bind a class implementing this interface under `SpeedySpec\WpPassword\PasswordChecker`. It then answers `wp_check_password()` for PHP and for Rust callers, until the request ends. <Ev test="speedyspec-wp-password-php::php::php_override_replaces_default"/> <Ev test="speedyspec-wp-password-php::php::rust_callers_get_the_php_override"/> <Ev test="speedyspec-wp-password-php::php::override_ends_with_the_request"/> An exception your method throws reaches the caller unchanged. <Ev test="speedyspec-wp-password-php::php::throwing_override_surfaces_as_php_exception"/> See the architecture page.

`SpeedySpec\WpPassword\application_password_check()` also uses the bound checker for any hash that isn't a `$generic$` fast hash. <Ev test="speedyspec-wp-password-php::php::application_check_uses_bound_checker"/>
