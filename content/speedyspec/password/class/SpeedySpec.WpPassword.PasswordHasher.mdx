## Behaviour

The PHP twin of the `PasswordHasher` port, which answers `wp_hash_password()`. Its one method, `hash( $password )`, hashes the password and returns the hash (or whatever you want `wp_hash_password()` to return). `#[php_port]` declares it at the start of every request from the Rust trait, so the two can't drift. <Ev source="ss:crates/speedyspec-wp-password-php/src/twins.rs#L10-L14" hash="37de9ec456e50fd1949bcbba855b47ee1b63c4b0726f88d6895de1bb389cbdc1"/>

## Override

Where WordPress lets a plugin declare `wp_hash_password()` first, bind a class implementing this interface under `SpeedySpec\WpPassword\PasswordHasher`. It then answers `wp_hash_password()` for PHP and for Rust callers, until the request ends. <Ev test="speedyspec-wp-password-php::php::php_override_replaces_default"/> <Ev test="speedyspec-wp-password-php::php::rust_callers_get_the_php_override"/> <Ev test="speedyspec-wp-password-php::php::override_ends_with_the_request"/> An exception your method throws reaches the caller unchanged. <Ev test="speedyspec-wp-password-php::php::throwing_override_surfaces_as_php_exception"/> See the architecture page.
