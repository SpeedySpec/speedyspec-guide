## Behaviour

Served by WordPress's PHP when PHP calls it: the release keeps it in `post.php`. The native [wp_insert_post()](/speedyspec/query/wp_insert_post/) runs the Rust rule below in its place, with its `wp_checkdate` filter, through the PHP clock adapter (`current_time()`, `get_date_from_gmt()`, PHP's own), and the `compat/posts-write` date scenarios replay exactly through it. <Ev scenario="insert-date-future" area="posts-write"/> <Ev scenario="insert-date-drafts" area="posts-write"/> <Ev scenario="update-date-edit-date" area="posts-write"/> <Ev source="ss:crates/speedyspec-wp-posts-php/src/release.rs#L14-L84" hash="15e4700faff81aa8c9b034cb34c2c038a2bac08fb0de928036549fb69d6ba78d"/>

## The Rust rule

`resolve_post_date` is `wp_resolve_post_date()` up to its `wp_checkdate` filter. An empty local date (`""`, `"0"` or the zero date) becomes now when the GMT date is empty too, else the GMT date in local time, both through the `Clock` port. Then `/^(\d{4})-(\d{1,2})-(\d{1,2})/`, anchored at the start only, and `checkdate()`, which is `gregorian_date_valid`. It answers `NoDate` when the pattern fails (false before any filter), else the whole date and whether `checkdate()` accepts it; `unfiltered()` is the answer with no `wp_checkdate` callback. <Ev source="ss:crates/speedyspec-wp-posts/src/dates.rs#L45-L72" hash="0506ffcaa5226347556f59cc2d7c2c39b1c9fcfff5f2187efeaf763e3cc71465"/> <Ev source="ss:crates/speedyspec-wp-posts/src/dates.rs#L104-L117" hash="546a0bf57395dfc807a8945f52791fc43a8e729dd9f44595fdb7f5ebd6c605b7"/>

The 15 recorded cases replay as in WordPress 7.2-RC2: empty and zero dates, dates from GMT under a timezone and an offset, a leap day and a non-leap 29 February, `2024-1-5 garbage` (kept whole, as the pattern is anchored only at its start), a two-digit year, month 13, year 0, 30 February, a leading space and letters. The replay's clock answers only what WordPress read, and fails if the rule asks for now where WordPress didn't. <Ev test="speedyspec-wp-posts::entity::dates_match_wordpress"/> <Ev test="speedyspec-wp-posts::entity::clock_refuses_now_where_none_was_recorded"/> <Ev source="ss:compat/posts-entity/record.php#L488-L505" hash="996185af4f61dd541247a7fc2d1a57d00663f14b3cb880451e4db254945674ec"/>

## Limits

- The rule returns the date and `checkdate()`'s verdict so the `wp_checkdate` filter, which the write use case runs, can change it.
- The time functions are the `Clock` port, which can fail now: an option filter that throws while the time zone is read stops the rule, as WordPress's exception would. The phase 2 replay answers from the recorded table; the write path's clock is the PHP adapter, and there is no Rust clock yet.
- Dates are bytes here, as PHP holds them; the write use case keeps them as PHP values until the row is written.
