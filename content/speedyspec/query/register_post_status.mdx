It parses `$args` with `wp_parse_args()` and the name with `sanitize_key()` and its filter, resolves the status with phase 2's rules, and stores the object in `$wp_post_statuses` through a PHP helper, so the global keeps PHP's key handling. <Ev scenario="statuses-register" area="posts-read"/> <Ev scenario="count-new-status" area="posts-read"/> <Ev test="speedyspec-wp-posts-php::registry::main"/>

The registries have no handler in the container: they are PHP's globals (`$wp_post_types`, `$wp_post_statuses`, `$_wp_post_type_features`), read and written live, so a handler would only wrap the global and there is nothing to rebind. ## The Rust rules

`PostStatusRegistry::register` runs `sanitize_key()` with no length check, so `register_post_status( '' )` stores `''`, then stores the object in its old place when the name is already registered, else at the end. `resolve_post_status` is the object: `array_merge()` over WordPress's defaults, `name` set, then the null defaults resolved in WordPress's order (`internal` when none of `public`, `internal`, `protected` and `private` is given, then `publicly_queryable`, `exclude_from_search`, the two admin list flags, `date_floating`, `label` and `label_count`). <Ev source="ss:crates/speedyspec-wp-posts/src/status.rs#L68-L73" hash="8a92681c16fa8f4d7c9f3a8700a75d885cabd732cbc01fe61d1a4992aeee9737"/> <Ev source="ss:crates/speedyspec-wp-posts/src/status.rs#L130-L136" hash="b1da3b27ba9637746b73f39ead4336934e8e55432dea4eeba85b24efd9a31441"/>

The 14 recorded status scenarios (19 calls) replay as in WordPress 7.2-RC2, and so do the 4 calls in the `lists` scenario, comparing each result and `$wp_post_statuses` in order. <Ev test="speedyspec-wp-posts::recorded::status_scenarios_match_wordpress"/> <Ev test="speedyspec-wp-posts::recorded::list_scenarios_match_wordpress"/>
