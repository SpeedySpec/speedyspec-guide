## Behaviour

Served by WordPress's PHP; the Rust rules below are not wired yet. The runtime worker links neither posts crate, so PHP on SpeedySpec runs WordPress's own `post.php` until phase 4 of the posts and meta port. <Ev source="ss:crates/speedyspec-php-runtime/Cargo.toml#L20-L55" hash="955f1ccec24cc11da3fa0826db96868561c6e6c3cdc55277b37b80c09b513508"/>

## The Rust rule

`post_types_by_support` keys each feature as `array_fill_keys()` does, so duplicates collapse, filters `$_wp_post_type_features` through the `PostTypeSupports` port with the list filter, and returns the post types left as a list (an integer-like post type is an int). <Ev source="ss:crates/speedyspec-wp-posts/src/list.rs#L192-L199" hash="f8909cea87470c8e1a4bafb129f5b035db2413820c9a97beaa9af9f1a21a98fa"/>

The 6 recorded calls in the `lists` scenario and 2 after `create_initial_post_types()` replay as in WordPress 7.1.5. <Ev test="speedyspec-wp-posts::recorded::list_scenarios_match_wordpress"/> <Ev test="speedyspec-wp-posts::recorded::initial_post_types_match_wordpress"/>

## Limits

- Recorded from WordPress 7.1.5 under the recorder's stubs: `__()` and `_x()` return their text, the rewrite functions do nothing, `register_taxonomy_for_object_type()` only notes its call, and `get_object_taxonomies()` returns nothing. <Ev source="ss:compat/posts/record.php#L53-L66" hash="6398e7220fdfb100a72b707de8a1729a005479e3dd92f38f53c6da72f86a0d8d"/>
- The rule takes the features as strings. WordPress keys `(array) $feature`'s values as PHP converts array keys, so phase 4's adapter converts them first.
