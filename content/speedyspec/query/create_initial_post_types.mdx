Native: `post.php`'s `create_initial_post_types()` is a line of PHP over `SpeedySpec\WpPosts\Native\create_initial_post_types`. <Ev source="ss:crates/speedyspec-wp-posts-php/src/post-types.php#L9-L12" hash="b1dab8c3ab380b69cf838edb43dfa8fcd34b624f795ee975b5a7dd09587180e7"/> <Ev source="ss:crates/speedyspec-wp-posts-php/src/registry.rs#L926-L962" hash="c9aa546fc8a36c83b1aad97c082112670869f5dd3fc68c43cfcbd5f7764503e2"/>

It runs phase 2's table of calls through the native `register_post_type()`, the support functions and `register_post_status()`, so their filters and actions fire as in WordPress. The globals it leaves are identical to the ones WordPress's own function leaves, run side by side from empty globals. <Ev test="speedyspec-wp-posts-php::registry::main"/> <Ev source="ss:crates/speedyspec-wp-posts-php/tests/registry.rs#L343-L348" hash="4b3296a717268201117eac24ec9dd8cc8dff28700537514a73cb26f2de884ef0"/> <Ev test="speedyspec-wp-posts-php::registry::main"/>

The registries have no handler in the container: they are PHP's globals (`$wp_post_types`, `$wp_post_statuses`, `$_wp_post_type_features`), read and written live, so a handler would only wrap the global and there is nothing to rebind. Change a registration with WordPress's own hooks. <Ev source="ss:crates/speedyspec-wp-posts-php/src/lib.rs#L16-L23" hash="cee2b8bc56cdb2f3c4038d6df9b3cd87ec0268ee2f97be22e1d5ff45d3187848"/>

No copied WordPress test calls it, so its proof is the recorded scenarios and the tests above.

## The Rust rule

`create_initial_post_types()` runs a table of steps against the two registries: the 16 post types in WordPress's order, with their arguments as PHP arrays in the source's key order and their labels through the `Translator` port; the supports calls WordPress makes between them; then the 12 statuses. As in WordPress 7.2, `post` is `randomable` and `page` and `attachment` are not, `post` and `page` are `show_in_abilities`, and `wp_block` supports `author` and isn't deleted with its author. <Ev source="ss:crates/speedyspec-wp-posts/src/initial.rs#L228-L236" hash="fb8661c711d024da3a626b87d8410238a63ad823806aa1f2c33d0bb7005ccaa2"/> <Ev source="ss:crates/speedyspec-wp-posts/src/initial.rs#L254-L260" hash="f03b26e00f0f6746166ee7217cd9fef4072ec569004846ec25a7bd25d4a63038"/> It reads one option, `wp_attachment_pages_enabled`, through `InitialOptions`, and returns each post type's registration, whose `future_{$post_type}` action and taxonomies the phase 4 adapter applies. <Ev source="ss:crates/speedyspec-wp-posts/src/initial.rs#L1-L7" hash="86f0928b0bf09d5a4d037d217764ae5ff3a3b6aa1b643c043066d68fff813a0c"/> <Ev source="ss:crates/speedyspec-wp-posts/src/initial.rs#L41-L48" hash="6c4af1bd6b1551bcfff515f9ac46cf94736fcdc89cabdbb16350a6875c633dcb"/>

Both recorded runs replay as in WordPress 7.2-RC2: one with no permalink structure and attachment pages off, one with `/%postname%/` and attachment pages on. Each compares `$wp_post_types`, `$_wp_post_type_features`, `$post_type_meta_caps` and `$wp_post_statuses` after the call, the actions it added, the taxonomies it registered, and 68 queries run after it (`get_post_types()`, `get_post_stati()`, `get_post_types_by_support()` and the viewable checks). <Ev test="speedyspec-wp-posts::recorded::initial_post_types_match_wordpress"/>

## Limits

- Recorded from WordPress 7.2-RC2 under the recorder's stubs: `__()` and `_x()` return their text, the rewrite functions do nothing, `register_taxonomy_for_object_type()` only notes its call, and `get_object_taxonomies()` returns nothing. <Ev source="ss:compat/posts/record.php#L53-L66" hash="6398e7220fdfb100a72b707de8a1729a005479e3dd92f38f53c6da72f86a0d8d"/>
- The labels are the `Translator` port's; only WordPress's English is recorded.
- It translates its labels before it registers anything; WordPress translates each type's as it registers it, so a `gettext` callback sees the same strings in another order.
