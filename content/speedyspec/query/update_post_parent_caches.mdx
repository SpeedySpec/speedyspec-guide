## Behaviour

Native: `post.php`'s `update_post_parent_caches()` is a line of PHP over `SpeedySpec\WpPosts\Native\update_post_parent_caches`, which dispatches the `UpdatePostParentCaches` message to the handler bound at `SpeedySpec\WpPosts\UpdatePostParentCachesHandler`, so a handler PHP binds there takes the call. <Ev source="ss:crates/speedyspec-wp-posts-php/src/posts.php#L150-L153" hash="0bd4c0866500eb098350d20b89dd162eceadf8f7824a5590277ba524e3b1fd7a"/> <Ev source="ss:crates/speedyspec-wp-posts/src/read/cache.rs#L399-L402" hash="2f1cff24e83f5daf00461f2145c5f2bbec86b38f59c84c509a665af0f856f175"/>

It plucks each post's `post_parent`, drops zeros and duplicates, and primes those parents with `_prime_post_caches( $ids, false )`: rows and meta, no terms. <Ev scenario="cache-update-parent-caches" area="posts-read"/> <Ev test="speedyspec-wp-posts-php::compat::main"/> <Ev test="speedyspec-wp-posts-tests::read::update_post_parent_caches_replays_recording"/>

No copied WordPress test calls it, so its proof is the recorded scenarios and the tests above.

## Differences

- **The meta statement.** This function reads post meta through the native meta functions, whose `update_meta_cache()` statement selects `meta_id` too (`SELECT meta_id, post_id, meta_key, meta_value …`, where WordPress sends `SELECT post_id, meta_key, meta_value …`), because the meta entity carries its id. A plugin that matches the exact text in a `query` filter misses it; the rows, the cache and the query count are WordPress's. It is the meta seam's documented difference, recorded here as a break on the scenarios that watch the statement. <Ev break="cache-prime-statement" step="1" area="posts-read"/> <Ev break="count-readable-statement" step="1" area="posts-read"/> <Ev source="ss:compat/posts-read/breaks.json#L1-L14" hash="c5f076b4794a20681d8b985e4d9fb2e12e1bda0c5f3b95a2ba59b4e080731c8d"/> See [update_meta_cache()](/speedyspec/meta/update_meta_cache/).
- **A negative parent.** The use case takes `Post` entities, whose parent is a `PostId`, so the PHP function reads a negative `post_parent` as its absolute value. WordPress keeps it until `_prime_post_caches()`. No recorded scenario or WordPress test has one. <Ev source="ss:crates/speedyspec-wp-posts-php/src/read.rs#L854-L874" hash="13532cdc20f8ca18b20432337ac04d9413d87b592835d0fd958372fbca5df876"/>
