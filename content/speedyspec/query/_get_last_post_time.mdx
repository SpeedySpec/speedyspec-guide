## Behaviour

Native: `post.php`'s `_get_last_post_time()` is a line of PHP over `SpeedySpec\WpPosts\Native\_get_last_post_time`, which dispatches the `GetLastPostTime` message to the handler bound at `SpeedySpec\WpPosts\GetLastPostTimeHandler`, so a handler PHP binds there takes the call. <Ev source="ss:crates/speedyspec-wp-posts-php/src/posts.php#L130-L133" hash="80424a61f636071f97e047ee6180d108808576a467d68622955990742fdd8997"/> <Ev source="ss:crates/speedyspec-wp-posts/src/read/counts.rs#L257-L262" hash="530e2f7b82503c029d3529e3acf68da62a63e2c0c932b995104a4b7d032b6fd8"/> <Ev source="ss:crates/speedyspec-wp-posts-sql/src/repository.rs#L548" hash="ef794a665dc5f123122618b61e7bc0929501321e985901a916da32b9448cc1ee"/>

It reads the `timeinfo` entry `lastpost{$field}:{$timezone}`, plus `:` and the `sanitize_key()`ed type when one is given; on a miss, the newest published date among the public post types (`any`) or the one given, in the clock `$timezone` names (lowercased; an unknown one sends no statement and answers false), cached when truthy. <Ev scenario="last-date-blog" area="posts-read"/> <Ev scenario="last-date-gmt" area="posts-read"/> <Ev scenario="last-date-server" area="posts-read"/> <Ev scenario="last-timezone-case" area="posts-read"/> <Ev scenario="last-type-key" area="posts-read"/> <Ev scenario="last-statement" area="posts-read"/> <Ev test="speedyspec-wp-posts-php::compat::main"/> <Ev test="speedyspec-wp-posts-tests::read::last_post_times_cache_and_compare"/> <Ev test="speedyspec-wp-posts-sql::engines::last_post_time_of_nothing_is_none_on_mysql"/>

WordPress's own `Tests_Post_GetLastPostDate`, `Tests_Post_GetLastPostModified` tests, copied from 7.2-RC2, pass against the port on a single site and on multisite. <Ev test="speedyspec-wp-posts-php::wordpress::wordpress_posts_runs_pass"/>

## Known breaks and open cases

- **`server` time and the 0.3.0 suite.** For `'server'` the statement reads the GMT column through `DATE_ADD( …, INTERVAL '0' SECOND )`, and MySQL answers with a fraction (`2024-03-01 20:00:00.000000`), which WordPress returns as it is and SpeedySpec does too. speedyspec-wp-posts-contracts 0.3.0's repository suite expects the text without it, so `speedyspec-wp-posts-sql`'s MySQL suite runs that one check as a known break until contracts 0.3.1 (speedyspec-platform PR #18) fixes the suite. It is the suite that is wrong, not the answer. <Ev test="speedyspec-wp-posts-sql::engines::server_time_keeps_mysql_fraction"/> <Ev test="speedyspec-wp-posts-sql::engines::suite_on_mysql"/>
