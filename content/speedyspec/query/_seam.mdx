Partly native. SpeedySpec answers three parts of this seam in Rust: `wpdb`, WordPress's database class (`class-wpdb.php`); post reading with the post type and post status registries; and the first post writers, `wp_insert_post()` and the functions beside it. Together they are 63 of `post.php`'s 147 functions. The rest of the seam (the other writers, the meta wrappers, `WP_Query` and its callers, comments, revisions, `WP`, the meta and date queries) is not ported yet: PHP on SpeedySpec still gets WordPress's own code for it, running over the native `$wpdb` and the native post functions.

## wpdb

- **Native:** the `wpdb` class with 70 of WordPress's 72 methods, every public and protected one, each handing its work to the Rust port (the two private ones, `_do_query()` and `_escape_identifier_value()`, have no counterpart); its six constants (`OBJECT`, `ARRAY_A` and the rest) and its filters (`query`, `incompatible_sql_modes`, `log_query_custom_data`, `pre_get_table_charset`, `pre_get_col_charset`). The worker declares it, and makes the global `$wpdb`, only when its environment names a database (`DB_NAME`, with `DB_USER`, `DB_PASSWORD`, `DB_HOST` and `TABLE_PREFIX`); without one it serves without the database. <Ev source="ss:crates/speedyspec-wp-db-php/src/lib.rs#L1-L15" hash="d5b7dc5a9da17bb3e83c07dbf4b6ee97e96ea41c938c7295d6a4528fe8861fc0"/> <Ev source="ss:crates/speedyspec-php-runtime/src/database.rs#L108-L111" hash="51d5dc2601480a74836de7ed4bafc49be66843644ce62413e09ce7cf1378ca98"/>
- **Verified:** WordPress's `wpdb`, recorded on MySQL (106 scenarios in `compat/wp-db/scenarios.json`), replays through the native class on MySQL, and again on SQLite and PostgreSQL. WordPress's own database tests (`db.php`, `db/charset.php`, `db/realEscape.php`, `db/dbDelta.php`; at least 652 tests) run against the port with the pinned PHPUnit and pass on MySQL. <Ev area="wp-db" scenario="query_returns"/> <Ev area="wp-db" scenario="readers_shapes"/> <Ev test="speedyspec-wp-db-php::wordpress::wordpress_db_tests_pass"/>
- **Documented differences (on every engine):** `$wpdb->dbh` is a `SpeedySpec\WpDb\Connection`, not a `mysqli`; the placeholder escape is removed in Rust, so no callback sits on `query`; and every statement is parsed before it runs, so a syntax error has the parser's wording, and one WordPress test, which creates a stored procedure the parser can't read, is skipped. <Ev area="wp-db" break="dbh_is_not_mysqli"/> <Ev area="wp-db" break="placeholder_escape_filter"/> <Ev area="wp-db" break="errors_syntax"/> <Ev source="ss:compat/wp-db/breaks.json#L19-L24" hash="242aab50df7115ec545a43d4f71ae98884da27dd7b522106efea8632b5ef0925"/>

### Engines

The worker builds its database from the MySQL engine only. The SQLite and PostgreSQL engines translate WordPress's MySQL statements and answer with MySQL's results; they pass the replay with two SQLite differences (a duplicate-key error's wording, and latin1 columns that keep any UTF-8 character), and WordPress's tests with 19 (SQLite) and 20 (PostgreSQL) listed failures, for conversions to non-Unicode charsets and, on PostgreSQL, spatial types. The worker can't use them yet. <Ev source="ss:crates/speedyspec-php-runtime/src/database.rs#L59-L73" hash="8b57e46fb27957a78cb8527c6a4fe6748c5ab4c70de3ef0fa15e05451118a7c4"/> <Ev source="ss:compat/wp-db/breaks.json#L25-L36" hash="069bce88f387e4c779c1b8e64767646303518de7f1b9896a325f2c5df734524e"/>

## Post reading and the registries

- **Native:** 55 of `post.php`'s functions, declared at the start of every request when the worker has a database, each a line of PHP over a native function: the 20 registry functions (`register_post_type()`, `register_post_status()`, their readers, the supports functions, the label and capability helpers, `create_initial_post_types()`), and 35 reading functions (`get_post()` and the readers beside it, the page functions, the counts and dates, the `posts` cache functions, `sanitize_post()` and `sanitize_post_field()`, the pings and `is_sticky()`). The reading functions dispatch through handlers bound in the container; the registries work on PHP's globals, live, and have none. `WP_Post` and `WP_Post_Type` stay WordPress's classes, except that the prepared release swaps `WP_Post::get_instance()`'s body for the native raw read. The post repository and the taxonomy calls are container ports PHP may rebind. <Ev source="ss:crates/speedyspec-wp-posts-php/src/lib.rs#L1-L34" hash="cdfed173b2d2841fe096873d0f5eae080cf9df26f5cd7de216b5d2a9e44bdf40"/> <Ev source="ss:crates/speedyspec-wp-posts-php/src/release.rs#L14-L84" hash="15e4700faff81aa8c9b034cb34c2c038a2bac08fb0de928036549fb69d6ba78d"/>
- **Verified against WordPress 7.2-RC2:** `compat/posts-read`'s 191 single-site and 5 multisite scenarios replay exactly through the native functions, and the 14 registry scenarios too. ## Writing posts

- **Native:** 8 more of `post.php`'s functions, declared beside the others: `wp_insert_post()`, `wp_update_post()`, `wp_transition_post_status()`, `set_post_type()`, and the default callbacks WordPress registers by name, `_transition_post_status()`, `_publish_post_hook()`, `_future_post_hook()` and `wp_check_post_hierarchy_for_loops()`. Each dispatches its message through a handler bound in the container, so PHP may rebind any of them. `wp_insert_post()` composes phase 2's date, loop, slug and trashed-suffix rules in WordPress's order. ## The post rules still WordPress's when PHP calls them

`wp_resolve_post_date()`, `wp_unique_post_slug()`, `wp_set_post_categories()` and the trashed-suffix functions run in Rust inside the native `wp_insert_post()`, but a plugin calling them gets WordPress's PHP. `_truncate_post_slug()`, `get_extended()`, `get_post_statuses()`, `get_page_statuses()`, `_wp_privacy_statuses()` and `_post_type_meta_capabilities()` have Rust rules proven against recordings, and stay WordPress's PHP. <Ev test="speedyspec-wp-posts::entity::slug_scenarios_match_wordpress"/> <Ev test="speedyspec-wp-posts::entity::dates_match_wordpress"/>

## Still WordPress's PHP

- **The `WP_Query` callers:** `get_posts()`, `get_children()`, `get_pages()` and `wp_get_recent_posts()`. They come with `WP_Query`'s port; `wp_insert_post()`'s trashed-suffix step reaches `get_posts()` through the `PostQuery` port meanwhile.
- **The other writers** (`wp_delete_post()`, the trash and untrash functions, `wp_publish_post()`, future posts, sticky posts, pings and auto-drafts), which phase 5b ports; **the meta wrappers** (`get_post_meta()` and the rest, over the native meta functions), `update_post_author_caches()` and the attachment readers.
- **Comments, revisions, `WP_Query`, `WP`, the meta and date queries,** and every query they build, which run over the native `$wpdb` and the native post functions.
