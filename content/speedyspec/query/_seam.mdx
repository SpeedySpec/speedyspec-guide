Partly native. SpeedySpec answers one part of this seam in Rust: `wpdb`, WordPress's database class (`class-wpdb.php`). The rest of the seam (posts, comments, revisions, `WP_Query`, `WP`, the meta and date queries, and their 339 functions) is not ported yet: PHP on SpeedySpec still gets WordPress's own code for it, running over the native `$wpdb`.

## wpdb

- **Native:** the `wpdb` class with 70 of WordPress's 72 methods, every public and protected one, each handing its work to the Rust port (the two private ones, `_do_query()` and `_escape_identifier_value()`, have no counterpart); its six constants (`OBJECT`, `ARRAY_A` and the rest) and its filters (`query`, `incompatible_sql_modes`, `log_query_custom_data`, `pre_get_table_charset`, `pre_get_col_charset`). The worker declares it, and makes the global `$wpdb`, only when its environment names a database (`DB_NAME`, with `DB_USER`, `DB_PASSWORD`, `DB_HOST` and `TABLE_PREFIX`); without one it serves without the database. <Ev source="ss:crates/speedyspec-wp-db-php/src/lib.rs#L1-L15" hash="d5b7dc5a9da17bb3e83c07dbf4b6ee97e96ea41c938c7295d6a4528fe8861fc0"/> <Ev source="ss:crates/speedyspec-php-runtime/src/database.rs#L93-L96" hash="51d5dc2601480a74836de7ed4bafc49be66843644ce62413e09ce7cf1378ca98"/>
- **Verified:** WordPress's `wpdb`, recorded on MySQL (106 scenarios in `compat/wp-db/scenarios.json`), replays through the native class on MySQL, and again on SQLite and PostgreSQL. WordPress's own database tests (`db.php`, `db/charset.php`, `db/realEscape.php`, `db/dbDelta.php`; at least 652 tests) run against the port with the pinned PHPUnit and pass on MySQL. <Ev area="wp-db" scenario="query_returns"/> <Ev area="wp-db" scenario="readers_shapes"/> <Ev test="speedyspec-wp-db-php::wordpress::wordpress_db_tests_pass"/>
- **Documented differences (on every engine):** `$wpdb->dbh` is a `SpeedySpec\WpDb\Connection`, not a `mysqli`; the placeholder escape is removed in Rust, so no callback sits on `query`; and every statement is parsed before it runs, so a syntax error has the parser's wording, and one WordPress test, which creates a stored procedure the parser can't read, is skipped. <Ev area="wp-db" break="dbh_is_not_mysqli"/> <Ev area="wp-db" break="placeholder_escape_filter"/> <Ev area="wp-db" break="errors_syntax"/> <Ev source="ss:compat/wp-db/breaks.json#L19-L24" hash="242aab50df7115ec545a43d4f71ae98884da27dd7b522106efea8632b5ef0925"/>
- **Not recorded as breaks:** a `wp-content/db.php` drop-in is refused, and `unset()` on one of `wpdb`'s declared public properties throws. See [wpdb](/speedyspec/query/class/wpdb/). <Ev test="speedyspec-wp-db-php::php::drop_in_refused"/>

### Engines

The worker builds its database from the MySQL engine only. The SQLite and PostgreSQL engines translate WordPress's MySQL statements and answer with MySQL's results; they pass the replay with two SQLite differences (a duplicate-key error's wording, and latin1 columns that keep any UTF-8 character), and WordPress's tests with 19 (SQLite) and 20 (PostgreSQL) listed failures, for conversions to non-Unicode charsets and, on PostgreSQL, spatial types. The worker can't use them yet. <Ev source="ss:crates/speedyspec-php-runtime/src/database.rs#L56-L70" hash="8b57e46fb27957a78cb8527c6a4fe6748c5ab4c70de3ef0fa15e05451118a7c4"/> <Ev source="ss:compat/wp-db/breaks.json#L25-L36" hash="069bce88f387e4c779c1b8e64767646303518de7f1b9896a325f2c5df734524e"/>

## Post types and statuses

Not native yet. speedyspec-server has `post.php`'s post type and post status rules and `WP_Post_Type`'s argument resolution in Rust (`speedyspec-wp-posts`), but the runtime worker doesn't link them, so all 24 of those functions and the class work as in WordPress. <Ev source="ss:crates/speedyspec-php-runtime/Cargo.toml#L24-L60" hash="4e45d1d171d753b4dfe1c47e78d7b37982c3572c9fc8cf407854fed9c53b58e9"/>

- **Proven against WordPress 7.2-RC2, not wired:** labels (12 cases), capabilities (9), `new WP_Post_Type()` (27), 12 post type and 14 status scenarios, the three status label tables, 87 list and predicate calls, and both runs of `create_initial_post_types()` with 68 queries after them, all from `compat/posts/cases.json`. <Ev test="speedyspec-wp-posts::recorded::post_type_scenarios_match_wordpress"/> <Ev test="speedyspec-wp-posts::recorded::list_scenarios_match_wordpress"/> <Ev test="speedyspec-wp-posts::recorded::initial_post_types_match_wordpress"/>
- **Not proven:** the hooks these functions fire, rewrite rules, taxonomy removal and the REST controllers, which the rules leave to phase 4 or to other seams, and WordPress's post PHPUnit tests. See the architecture page.

## The post entity, dates, slugs and hierarchy

Not native yet. speedyspec-server has the `Post` entity, its repository and mapper, and 11 of this seam's `post.php` functions in Rust: `wp_resolve_post_date()`, `wp_unique_post_slug()`, `_truncate_post_slug()` (through the text seam's `wp_truncate_slug()`), `wp_get_post_parent_id()`, `wp_check_post_hierarchy_for_loops()`, `get_post_ancestors()`, `get_page_uri()`, `get_page_hierarchy()`, `_page_traverse_name()`, `get_page_children()` and `get_extended()`, with the Support seam's `wp_find_hierarchy_loop()` and its tortoise and hare. The runtime worker links no posts crate, so all of them work as in WordPress. <Ev source="ss:crates/speedyspec-php-runtime/Cargo.toml#L24-L60" hash="4e45d1d171d753b4dfe1c47e78d7b37982c3572c9fc8cf407854fed9c53b58e9"/>

- **Proven against WordPress 7.2-RC2, not wired:** 15 date cases, 8 slug scenarios (40 calls), 21 hierarchy calls, 16 page tree calls and 10 `get_extended()` cases from `compat/posts-entity/cases.json`, each replay comparing the result and, where WordPress reads the database, its statements in order; and the rows and cache entries the mapper reads. <Ev test="speedyspec-wp-posts::entity::slug_scenarios_match_wordpress"/> <Ev test="speedyspec-wp-posts::entity::hierarchy_matches_wordpress"/> <Ev test="speedyspec-wp-posts-sql::mapper::cache_reads_match_wordpress"/>
- **Not proven:** the filters these functions run, which phase 4 adds; MySQL's case-insensitive collation, since the recorder's stub `$wpdb` compares bytes; the page trees over a cycle, where PHP never ends and the port stops at the first revisit; and WordPress's post PHPUnit tests.
- **Not composed:** `wp_insert_post()`. Phase 5 runs its steps in WordPress's order, from these rules: the date, the hierarchy check with its `wp_update_post()` calls, the slug, the `import_id` check, then the insert. See the architecture page.

## Still WordPress's PHP

The `wp-db` scenarios and tests cover `wpdb` only. Everything else in this seam, and every query it builds, is WordPress's PHP calling the native `$wpdb`.
