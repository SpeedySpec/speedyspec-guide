Partly native. SpeedySpec answers two parts of this seam in Rust: `wpdb`, WordPress's database class (`class-wpdb.php`), and post reading with the post type and post status registries, 55 of `post.php`'s 147 functions. The rest of the seam (post writes, the meta wrappers, `WP_Query` and its callers, comments, revisions, `WP`, the meta and date queries) is not ported yet: PHP on SpeedySpec still gets WordPress's own code for it, running over the native `$wpdb` and the native post functions.

## wpdb

- **Native:** the `wpdb` class with 70 of WordPress's 72 methods, every public and protected one, each handing its work to the Rust port (the two private ones, `_do_query()` and `_escape_identifier_value()`, have no counterpart); its six constants (`OBJECT`, `ARRAY_A` and the rest) and its filters (`query`, `incompatible_sql_modes`, `log_query_custom_data`, `pre_get_table_charset`, `pre_get_col_charset`). The worker declares it, and makes the global `$wpdb`, only when its environment names a database (`DB_NAME`, with `DB_USER`, `DB_PASSWORD`, `DB_HOST` and `TABLE_PREFIX`); without one it serves without the database. <Ev source="ss:crates/speedyspec-wp-db-php/src/lib.rs#L1-L15" hash="d5b7dc5a9da17bb3e83c07dbf4b6ee97e96ea41c938c7295d6a4528fe8861fc0"/> <Ev source="ss:crates/speedyspec-php-runtime/src/database.rs#L104-L107" hash="51d5dc2601480a74836de7ed4bafc49be66843644ce62413e09ce7cf1378ca98"/>
- **Verified:** WordPress's `wpdb`, recorded on MySQL (106 scenarios in `compat/wp-db/scenarios.json`), replays through the native class on MySQL, and again on SQLite and PostgreSQL. WordPress's own database tests (`db.php`, `db/charset.php`, `db/realEscape.php`, `db/dbDelta.php`; at least 652 tests) run against the port with the pinned PHPUnit and pass on MySQL. <Ev area="wp-db" scenario="query_returns"/> <Ev area="wp-db" scenario="readers_shapes"/> <Ev test="speedyspec-wp-db-php::wordpress::wordpress_db_tests_pass"/>
- **Documented differences (on every engine):** `$wpdb->dbh` is a `SpeedySpec\WpDb\Connection`, not a `mysqli`; the placeholder escape is removed in Rust, so no callback sits on `query`; and every statement is parsed before it runs, so a syntax error has the parser's wording, and one WordPress test, which creates a stored procedure the parser can't read, is skipped. <Ev area="wp-db" break="dbh_is_not_mysqli"/> <Ev area="wp-db" break="placeholder_escape_filter"/> <Ev area="wp-db" break="errors_syntax"/> <Ev source="ss:compat/wp-db/breaks.json#L19-L24" hash="242aab50df7115ec545a43d4f71ae98884da27dd7b522106efea8632b5ef0925"/>
- **Not recorded as breaks:** a `wp-content/db.php` drop-in is refused, and `unset()` on one of `wpdb`'s declared public properties throws. See [wpdb](/speedyspec/query/class/wpdb/). <Ev test="speedyspec-wp-db-php::php::drop_in_refused"/>

### Engines

The worker builds its database from the MySQL engine only. The SQLite and PostgreSQL engines translate WordPress's MySQL statements and answer with MySQL's results; they pass the replay with two SQLite differences (a duplicate-key error's wording, and latin1 columns that keep any UTF-8 character), and WordPress's tests with 19 (SQLite) and 20 (PostgreSQL) listed failures, for conversions to non-Unicode charsets and, on PostgreSQL, spatial types. The worker can't use them yet. <Ev source="ss:crates/speedyspec-php-runtime/src/database.rs#L57-L71" hash="8b57e46fb27957a78cb8527c6a4fe6748c5ab4c70de3ef0fa15e05451118a7c4"/> <Ev source="ss:compat/wp-db/breaks.json#L25-L36" hash="069bce88f387e4c779c1b8e64767646303518de7f1b9896a325f2c5df734524e"/>

## Post reading and the registries

- **Native:** 55 of `post.php`'s functions, declared at the start of every request when the worker has a database, each a line of PHP over a native function: the 20 registry functions (`register_post_type()`, `register_post_status()`, their readers, the supports functions, the label and capability helpers, `create_initial_post_types()`), and 35 reading functions (`get_post()` and the readers beside it, the page functions, the counts and dates, the `posts` cache functions, `sanitize_post()` and `sanitize_post_field()`, the pings and `is_sticky()`). The reading functions dispatch through handlers bound in the container; the registries work on PHP's globals, live, and have none. `WP_Post` and `WP_Post_Type` stay WordPress's classes, except that the prepared release swaps `WP_Post::get_instance()`'s body for the native raw read. The post repository and the taxonomy calls are container ports PHP may rebind. <Ev source="ss:crates/speedyspec-wp-posts-php/src/lib.rs#L1-L23" hash="cbc9bc0315ac43f0e1d7e61a17c513afca658d16aaa1d190fd128a04600623a1"/> <Ev source="ss:crates/speedyspec-wp-posts-php/src/release.rs#L14-L74" hash="2b3494c571a6a44e50d757bea931bec2c8ee3b909e5e1d940b153db3026b04c2"/>
- **Verified against WordPress 7.2-RC2:** `compat/posts-read`'s 191 single-site and 5 multisite scenarios replay exactly through the native functions, and the 14 registry scenarios too. WordPress's own post PHPUnit tests (20 files, 235 tests on a single site and 235 on multisite) pass with no failures, errors or skips. <Ev test="speedyspec-wp-posts-php::compat::main"/> <Ev test="speedyspec-wp-posts-php::registry::main"/> <Ev test="speedyspec-wp-posts-php::wordpress::wordpress_posts_runs_pass"/> <Ev scenario="get-by-id" area="posts-read"/> <Ev scenario="page-path-nested" area="posts-read"/> <Ev scenario="count-posts-each" area="posts-read"/> <Ev scenario="cache-clean-post" area="posts-read"/> <Ev scenario="ms-cache-switch" area="posts-read"/>
- **Not run:** five WordPress tests are left out, because they need `go_to()` (2), taxonomy writes (2) or file uploads (1), none of which is loaded. They are untested, not different. <Ev source="ss:crates/speedyspec-wp-posts-php/tests/wordpress.rs#L101-L166" hash="a72cd183bb0db176632c0d6eb538a55596678397fb6692875c10c885385f3601"/>
- **Documented differences:** the meta statement those reads trigger selects `meta_id` too (the meta seam's difference); `_prime_post_caches()` and `_prime_post_parent_id_caches()` drop a negative id WordPress keeps in its `IN (…)`, and the Rust contract's typed ids can't hold `-1` or `"x"`; and objects handed to a reading function's hook callbacks are copies. <Ev break="cache-prime-statement" step="1" area="posts-read"/> <Ev break="count-readable-statement" step="1" area="posts-read"/>
- **Open cases:** the statements with no `ORDER BY` (`get_all_page_ids()`, `wp_count_attachments()`, `get_available_post_mime_types()`) match on MySQL 9.6, with CI's MySQL 8.4 run still to come. <Ev test="speedyspec-wp-posts-sql::engines::server_time_keeps_mysql_fraction"/>
- **Speed:** a warm `get_post()` is at parity with WordPress (0.94 µs against 0.92 µs), a cold one ties; `get_post_meta()` is 2.5× WordPress, pending speedyspec-platform fixes. See the architecture page. <Ev source="ss:crates/speedyspec-wp-posts-php/benches/read.rs#L1-L18" hash="d5e4a5cc2f244e75f14fca0c9f669e61e397f8a926c6d3f909e8160fb07d6081"/>

## The post rules not yet called

Phase 2's dates, slugs, loop check and `get_extended()` rules are in Rust (`speedyspec-wp-posts`), proven against recordings, but `wp_resolve_post_date()`, `wp_unique_post_slug()`, `_truncate_post_slug()`, `wp_check_post_hierarchy_for_loops()` and `get_extended()` stay WordPress's PHP, as do `get_post_statuses()`, `get_page_statuses()`, `_wp_privacy_statuses()` and `_post_type_meta_capabilities()`. Phase 5 composes `wp_insert_post()` from them. <Ev test="speedyspec-wp-posts::entity::slug_scenarios_match_wordpress"/> <Ev test="speedyspec-wp-posts::entity::dates_match_wordpress"/>

## Still WordPress's PHP

- **The `WP_Query` callers:** `get_posts()`, `get_children()`, `get_pages()`, `wp_get_recent_posts()`, and the trashed-suffix step of `wp_insert_post()`. They come with `WP_Query`'s port.
- **The post writes, the meta wrappers** (`get_post_meta()` and the rest, over the native meta functions), `update_post_author_caches()` and the attachment readers.
- **Comments, revisions, `WP_Query`, `WP`, the meta and date queries,** and every query they build, which run over the native `$wpdb` and the native post functions.
