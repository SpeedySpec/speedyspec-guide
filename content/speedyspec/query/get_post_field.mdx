## Behaviour

Native: `post.php`'s `get_post_field()` is a line of PHP over `SpeedySpec\WpPosts\Native\get_post_field`, which dispatches the `GetPostField` message to the handler bound at `SpeedySpec\WpPosts\GetPostFieldHandler`, so a handler PHP binds there takes the call. <Ev source="ss:crates/speedyspec-wp-posts-php/src/posts.php#L35-L38" hash="202d29c0f54abf283355c5303857de977e522b4df770a25dbe3fa35ef5817bd6"/> <Ev source="ss:crates/speedyspec-wp-posts/src/read/get.rs#L286-L290" hash="6d6db2045a5f7ffe15c3931faec386dfc6f2bd0955c68c4f0103c338ee7faefb"/>

It reads the post, then the field as `WP_Post` would give it: a property as it is (a present `null` is `''`), else `WP_Post::__isset()` and `__get()`'s branches, `ancestors`, `page_template` (post meta `_wp_page_template`), `post_category` and `tags_input` (through the `Taxonomy` port), then any post meta key (`metadata_exists()`, then the first value). ## Differences

- **An object argument is read as a copy.** The readers beside `get_post()` hand an object argument to the use case as a copy, for one dispatch. WordPress's `get_post()` inside them sanitizes a `stdClass` with no `filter` in place, setting `filter` to `raw` and casting its ids to int; on SpeedySpec the caller's object is left as it was. The answer is the same. Not recorded. <Ev source="ss:crates/speedyspec-wp-posts-php/src/read.rs#L30-L34" hash="2bc082f37a3aa63398531ebb37534e185fe71501b2fbacd16834877684966948"/>
