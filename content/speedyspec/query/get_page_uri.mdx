## Behaviour

Native: `post.php`'s `get_page_uri()` is a line of PHP over `SpeedySpec\WpPosts\Native\get_page_uri`, which dispatches the `GetPageUri` message to the handler bound at `SpeedySpec\WpPosts\GetPageUriHandler`, so a handler PHP binds there takes the call. <Ev source="ss:crates/speedyspec-wp-posts-php/src/posts.php#L115-L118" hash="862d1aa5a8699ff8cf6a41321eb35f748f68fb4c15c8dd8d97721f027a1e19f5"/> <Ev source="ss:crates/speedyspec-wp-posts/src/read/pages.rs#L235-L237" hash="d4408ab44b7caf5e851b3ed4055f5fe1f6d1a757f8dd8296e73705621c4f55a2"/>

It reads the page with `get_post()` (false when there is none), builds the path of ancestor names with phase 2's `page_uri` rule over the cached reads, and runs the `get_page_uri` filter with `( $uri, $page )`. <Ev scenario="page-uri-nested" area="posts-read"/> <Ev scenario="page-uri-encoded" area="posts-read"/> <Ev scenario="page-uri-loop" area="posts-read"/> <Ev scenario="page-uri-missing" area="posts-read"/> <Ev scenario="page-uri-empty-name" area="posts-read"/> <Ev scenario="page-uri-object" area="posts-read"/> <Ev scenario="page-uri-global" area="posts-read"/> <Ev scenario="page-uri-filter" area="posts-read"/> <Ev test="speedyspec-wp-posts-php::compat::main"/>

WordPress's own `Tests_Post_GetPageUri` tests, copied from 7.2-RC2, call it and pass against the port on a single site and on multisite. <Ev test="speedyspec-wp-posts-php::wordpress::wordpress_posts_runs_pass"/>

## Differences

- **An object argument is read as a copy.** The readers beside `get_post()` hand an object argument to the use case as a copy, for one dispatch. WordPress's `get_post()` inside them sanitizes a `stdClass` with no `filter` in place, setting `filter` to `raw` and casting its ids to int; on SpeedySpec the caller's object is left as it was. The answer is the same. Not recorded. <Ev source="ss:crates/speedyspec-wp-posts-php/src/read.rs#L30-L34" hash="2bc082f37a3aa63398531ebb37534e185fe71501b2fbacd16834877684966948"/>
- **Objects in hook arguments are copies.** The use cases carry PHP values, and `PhpValueHooks` makes them PHP values on the way into a hook, so a callback gets an equal object of the same class, not the one WordPress would hand it. An object a callback returns crosses back as it is (a `stdClass` as an equal copy). Meta has the same limit. <Ev source="ss:crates/speedyspec-wp-posts-php/src/hooks.rs#L1-L12" hash="7b8ef1e169180452a8fca24ae7ada72bff898f2dbf6d0efc07fc98d66d328069"/> <Ev test="speedyspec-wp-posts-php::errors::main"/>

## The Rust rule

`page_uri` is `get_page_uri()` before its `get_page_uri` filter, for a page already read: each ancestor's name, then `/`, nearest last, before the page's own name. An ancestor named `""` or `"0"` is false in PHP and left out. As in WordPress, `$page->ancestors` reads every ancestor, then each one is read again for its name. <Ev source="ss:crates/speedyspec-wp-posts/src/hierarchy.rs#L162-L176" hash="9580e160ea1319a8723ac2909f28debb657df6f121321ba350f8604abfa13701"/>

The 4 recorded calls replay as in WordPress 7.2-RC2, comparing the URI and every post read, in order: a deep page under an ancestor with an empty name, with a percent-encoded name of its own, a middle page, a top-level page and a missing page (false). <Ev test="speedyspec-wp-posts::entity::hierarchy_matches_wordpress"/> <Ev source="ss:compat/posts-entity/record.php#L634-L671" hash="6f47b85147282bdf090f33ec9af0e325f028a7ac61bc8eb02647a03f03402cde"/>
