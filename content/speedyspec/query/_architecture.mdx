Three parts of this seam are native: `wpdb`, with the data layer under it; post reading with the post type and post status registries; and the first post writers, `wp_insert_post()` and the functions beside it, 63 of `post.php`'s functions in all. Comments, `WP_Query`, the other writers and the rest of the seam aren't ported yet. This page covers `wpdb` and the data layer, post reading, post writing, and the post rules of phases 2a and 2b underneath them.

## wpdb

### The domain and its ports

`speedyspec-wp-db` is `class-wpdb.php` in Rust. `NativeWpdb` is its API (a Gateway) and the handler of every command and query; pure domain services hold WordPress's rules (`prepare()`'s placeholders, escaping, table names and prefixes, charsets, the field formats of `insert()` and `update()`). It has two outbound ports. <Ev source="ss:crates/speedyspec-wp-db/src/lib.rs#L1-L4" hash="d894ca48cf18e0364180a46d523b5d65135ecb9819150b2b9ecf9195373ce936"/>

- **`WpdbState`**: what `wpdb` keeps between calls in one request (`last_query`, `last_result`, `num_rows`, `insert_id`, `last_error`, the query log, and the rest), read and changed only through it. <Ev source="ss:crates/speedyspec-wp-db/src/state.rs#L84-L92" hash="4d2acdbf104fa8655257601e75b598160e78d69e14e233e9278bf6a8a64037f0"/>
- **`WpdbHost`**: what only WordPress's PHP can do for `wpdb`: `_doing_it_wrong()`, `__()`, constants, `is_multisite()`, `error_log()`, output, `wp_die()`, `dead_db()`, `$EZSQL_ERROR` and the caller summary. <Ev source="ss:crates/speedyspec-wp-db/src/host.rs#L9-L23" hash="2968b0eb93623ab1f9424735e372724d3dd7387840e98f5cfbcba4ae0b9a51f0"/>

`NativeWpdb` is built from a `SqlStore` (the data layer's contract below), the Hook API, a state, a host and the database settings (`WpDbConfig`). It wraps the store in `TimedSqlStore`, which times each statement for `$wpdb->queries`. <Ev source="ss:crates/speedyspec-wp-db/src/timed.rs#L1-L1" hash="5d1192632de4974c91504aaec7e81a051995896bf57bbacd406083db14989faa"/>

### The contracts

`speedyspec-wp-db-contracts` holds `Wpdb`, the port other seams call: the 11 `wpdb` methods they use (`table_name()`, `query_statement()`, `query_bytes()`, `prepare()`, `process_fields()`, `insert()`, `update()`, `delete()`, `insert_id()`, `suppress_errors()` and `charset()`), each named after the `wpdb` method it is. <Ev source="ss:crates/speedyspec-wp-db-contracts/src/api.rs#L7-L11" hash="0cd8c29e96a07ce1d2bc47d2d6d6a99c8da70ef7af15259c39b3208c0b2e6c8a"/> The values it hands out moved there from `speedyspec-wp-db`: `QueryOutcome` and `WpRow` (from `shape.rs`), `Field`, `ColLength` and `LengthKind` (from `fields.rs`), and `WpDbError` with `take_hook_error()` (from `error.rs`). A hook callback's failure converts into `WpDbError` with `From`, which also records it in a thread-local slot; the `-php` bridges take it from there to rethrow the PHP exception. <Ev source="ss:crates/speedyspec-wp-db-contracts/src/error.rs#L96-L98" hash="640372d4ae12f8e8722d08f2824c7f93b7011d8402fc702e1f54a360e83d3a99"/>

`NativeWpdb` implements the port. Each method calls `NativeWpdb`'s own by its full path, so none can call itself. <Ev source="ss:crates/speedyspec-wp-db/src/contract.rs#L1-L8" hash="ad84ee484c8ad0f6cd3476f2614e91001e3e0df3e6742cab88410395ee42ae3d"/> <Ev test="speedyspec-wp-db::contract::every_method_reaches_wpdb_through_dyn"/> <Ev test="speedyspec-wp-db::contract::hook_error_through_wpdb_is_taken_once"/> Options' SQL repositories hold `Rc<dyn Wpdb>`, and `speedyspec-wp-options-sql` depends on `speedyspec-wp-db` only for its tests. <Ev source="ss:crates/speedyspec-wp-options-sql/src/repository.rs#L20" hash="33ac78a2d0182fd737625b429df0c3e8712365e27573215d568d65bff8a2e46e"/> <Ev source="ss:crates/speedyspec-wp-options-sql/Cargo.toml#L14-L22" hash="63498faf303b7be20f8a5cf36432d69986772a3f47c545f9d3466e4780c58f31"/> The worker builds the one `NativeWpdb` and hands it to them, so they get the same `wpdb` PHP uses.

### The use cases

Every `wpdb` method is a command or a query, bound in the container under `SpeedySpec\WpDb\<Name>Handler`. The readers take no SQL: `get_var( $sql )` is the `Query` command followed by the `GetVar` query. <Ev source="ss:crates/speedyspec-wp-db/src/messages.rs#L1-L4" hash="c79ce199c4f8844f92f6f00ea5a752157681ec747c77ce7c73eabbd156e80299"/> <Ev test="speedyspec-wp-db::messages::every_key_is_bound"/>

- **Commands (13):** `Query`, `Insert`, `Replace`, `Update`, `Delete`, `SetPrefix`, `SetBlogId`, `SetCharset`, `SetSqlMode`, `Select`, `Flush`, `Close`, `CheckConnection`.
- **Queries (18):** `PrepareSql`, `EscLike`, `Escape`, `GetVar`, `GetRow`, `GetCol`, `GetResults`, `GetColInfo`, `GetTableCharset`, `GetColCharset`, `GetColLength`, `GetBlogPrefix`, `Tables`, `HasCap`, `DbVersion`, `DbServerInfo`, `SupportsCollation`, `GetCharsetCollate`.

`register_wpdb_handlers()` binds one `NativeWpdb` as the handler of all 31. <Ev source="ss:crates/speedyspec-wp-db/src/messages.rs#L133-L140" hash="6adc52a692119264ad60d9013e0d2edff2944b1379303ec04eca496bd46597ab"/> <Ev test="speedyspec-wp-db::messages::dispatch_reaches_wpdb"/>

### Two ways in: SQL text and statements

- **`NativeWpdb::query()`** takes SQL text, as `$wpdb->query()` does. The placeholder escape is removed, the `query` filter runs, and the text is parsed into a statement. Text the parser rejects still counts as a query and sets `last_error`. <Ev test="speedyspec-wp-db::helpers::parse_failure_counts_as_a_query"/>
- **`NativeWpdb::query_statement()`** takes a statement a ported API built. When nothing is hooked on `query`, the statement goes to the store as built, with no text in between; when a callback is, the statement is rendered as text, filtered and parsed again, so a PHP `query` callback still sees every statement. <Ev source="ss:crates/speedyspec-wp-db/src/api.rs#L287-L289" hash="7bcdc56fdb206ae0e1ab12b24e998fadb1314896ea0215fb83ccd87802d6cd23"/> <Ev test="speedyspec-wp-db::query::query_statement_fast_path"/> <Ev test="speedyspec-wp-db::query::query_statement_reparses_with_callback"/>

Both then run the Rust-only filter `speedyspec_query_statement`, whose callbacks receive and return the statement itself, before it is executed. <Ev source="ss:crates/speedyspec-wp-db/src/api.rs#L390-L391" hash="42567cd6ddcefece76ff9621cac1ae3fbcc23db8f683a43549504aacbc5a6ea2"/> <Ev test="speedyspec-wp-db::query::statement_hook_replaces_tree"/>

### Its adapters

- **The PHP area** (`WpDbArea`, in `speedyspec-wp-db-php`): at the start of every request it declares `wpdb`'s constants and the `wpdb` class, each method one line calling a native function under `SpeedySpec\WpDb\Native\` with the instance's handle, then makes the global `$wpdb` (handle 0) and connects it. The class converts values and holds no rules. <Ev source="ss:crates/speedyspec-wp-db-php/src/lib.rs#L1-L15" hash="d5b7dc5a9da17bb3e83c07dbf4b6ee97e96ea41c938c7295d6a4528fe8861fc0"/> <Ev test="speedyspec-wp-db-php::wordpress::wordpress_db_tests_pass"/>
- **The global's state** is the worker's memory state (`MemoryWpdbState`), bound under `SpeedySpec\WpDb\WpdbState` and read through the container on every access, so a state bound under that key replaces it. <Ev source="ss:crates/speedyspec-wp-db-php/src/lib.rs#L76-L92" hash="3eb4cc0b90504bb6ebb686a2907f0e510533ee2d312188d724968118e3796e39"/>
- **`PhpWpdbState`** adapts a PHP object implementing `SpeedySpec\WpDb\WpdbState` to the state port. <Ev source="ss:crates/speedyspec-wp-db-php/src/state.rs#L46-L48" hash="12988c198090decc6eaded3801b2383d291fab570cd41dd257bda1d6bda80000"/> <Ev test="speedyspec-wp-db-php::php::php_state_twin_replaces_memory"/>
- **`PhpWpdbHost`** is the host port over WordPress's PHP functions, with WordPress's own fallbacks when one isn't defined; `MemoryWpdbHost` records every call, for tests and hosts without WordPress. <Ev source="ss:crates/speedyspec-wp-db-php/src/host.rs#L1-L1" hash="e0f7d3820aaf79e8a653c3283924c2f2439ce3222bb7b692329ba385f415f492"/>
- **Another `new wpdb(...)`** gets its own `NativeWpdb`, with a memory state, on an engine configured once per worker for its credentials. <Ev source="ss:crates/speedyspec-wp-db-php/src/lib.rs#L131-L132" hash="9ac80f8673589f24e3732fc5bbb85e8f00680578ce79b8905bd0d8ede4acf09e"/>

The worker builds the `default` engine from its database settings with the MySQL factory, checks it with `SELECT 1`, then registers `WpDbArea` before the object cache, options and cron areas; options is given its `NativeWpdb`, which its repositories hold as the `Wpdb` port. <Ev source="ss:crates/speedyspec-php-runtime/src/database.rs#L59-L73" hash="8b57e46fb27957a78cb8527c6a4fe6748c5ab4c70de3ef0fa15e05451118a7c4"/>

## The data layer

`wpdb`'s store is the data layer's `SqlStore`, and every runtime feature that keeps data reaches its engine through the same contracts.

### Contracts

`speedyspec-data` holds only contracts: values and rows, the statement model (a Query Object over `sqlparser`'s tree), the SQL, NoSQL and Direct store contracts, dialects, engines, and the Repository and Unit of Work contracts. <Ev source="ss:crates/speedyspec-data/src/lib.rs#L5-L9" hash="cf4681992d0ea65f1e2a7734854c7bf989e847c7c87a223ebb03800a469f8f78"/> <Ev test="speedyspec-data::contracts::contracts_are_object_safe"/>

- **`SqlStore`**: a relational store that takes statements only (a caller with SQL text parses it first), with transactions, savepoints, an `Introspector` that answers in MySQL's terms, and `reset()`, which the runtime calls at the end of every request. <Ev source="ss:crates/speedyspec-data/src/store.rs#L44-L63" hash="fc943fa1d5ae00f75d6589fe8cf5bf8c888e9c2416e344449d34120b6e17a456"/>
- **`NoSqlStore`**: byte keys and values in named keyspaces, with expiry, atomic `put_if_absent`, counters and ranges. <Ev source="ss:crates/speedyspec-data/src/store.rs#L68-L69" hash="1b011551e49ab37fb246e142168897df09a5549e3a30b8f7b2289b9f0911cd90"/>
- **`DirectStore`**: any other storage system, reached through its own client, which a repository gets with `as_any()`. <Ev source="ss:crates/speedyspec-data/src/store.rs#L118-L119" hash="5143496a61ec74feb7965595409b7264dd8f7cde2ad51573f663db429672e028"/>
- **`EngineFactory`, `Engine` and `EngineLookup`**: a factory per URL scheme builds an engine from its configuration; opening it gives a SQL, NoSQL or Direct handle. <Ev source="ss:crates/speedyspec-data/src/engine.rs#L59-L76" hash="0f79e106166e8858cf63f2497905aedea7a0efa7a1e5112bca16058deabdb441"/>

### Building and routing statements

`speedyspec-data-query` parses every statement with MySQL's dialect; there is no pass-through path. <Ev source="ss:crates/speedyspec-data-query/src/lib.rs#L1-L3" hash="fc4de0c75313d31a9ed5c63dd90c167687fed54274332e53dd1b694ded0d0e34"/> It holds:

- **`Query`**, the query builder: `Query::table()`, `insert_into()`, `replace_into()`, `update()` and `delete_from()`, with `select()`, `where_eq()`, `where_in()`, `order_by()`, `limit()`, `offset()`, `values()`, `set()` and `on_duplicate_update()`. Values become statement parameters, never text. `build()` gives the statement, or the first error a modifier met. <Ev test="speedyspec-data-query::builder::select_with_where_in"/> <Ev test="speedyspec-data-query::builder::misuse_is_reported_at_build"/>
- **`EngineRegistry`**, the worker's engines. A use (such as `object-cache`) goes to the engine it is routed to, else to `default`; each engine opens once and lives for the worker. <Ev source="ss:crates/speedyspec-data-query/src/registry.rs#L71-L84" hash="45c345d78c15fdb24dbe24fb7f0fb5e47b8fa8d47ee2ae43cca3234c4d63a3de"/> <Ev test="speedyspec-data-query::registry::registry_routes_and_opens_once"/>
- **`PassChain`**, the rewrite passes an engine runs on a statement before it sends it. <Ev test="speedyspec-data-query::passes::passes_run_in_order_and_split"/>

## Patterns

- **Gateway** for `NativeWpdb`, the one entry to the database for PHP and Rust; other seams reach it through the `Wpdb` port (**Ports and Adapters**).
- **Command and query handlers** (CQRS) for each `wpdb` method, registered in the container (**Registry**).
- **Ports and Adapters** for the request state (`WpdbState`: memory and PHP) and for the host (`WpdbHost`, a **Strategy**: PHP and memory).
- **Facade** for the PHP `wpdb` class over the native functions; its public properties are PHP property hooks over the port.
- **Decorator** for `TimedSqlStore` over the engine's store.
- **Query Object** for `Statement`, **Builder** for `Query`, and **Interpreter** for parsing every statement.
- **Abstract Factory** for engines, **Strategy** for dialects, and **Chain of Responsibility** with **Visitor** for the rewrite passes.
- **Unit of Work** and **Identity Map** for multi-engine writes; **Repository** for the features that store entities (options' `SqlOptionRepository`, for one).

## A runtime feature calling it

A feature holds the `Wpdb` port, not `NativeWpdb`, so it depends only on `speedyspec-wp-db-contracts`. The worker hands it the global `wpdb` when it boots (options gets it from `WpDbArea::api()`). The feature builds its statement with the query builder and runs it with `query_statement()`, as `SqlOptionRepository` does. <Ev source="ss:crates/speedyspec-wp-options-sql/src/repository.rs#L134-L150" hash="7adcdc1ac78889faa40edbaa3e87d29b82eeaaefe8931e6930df46d176ccb5ec"/>

```rust
use std::rc::Rc;

use speedyspec_data_query::Query;
use speedyspec_wp_db_contracts::{QueryOutcome, WpDbError, Wpdb};

/// Reads one setting from a table the feature owns.
pub struct GuideSettings {
    wpdb: Rc<dyn Wpdb>,
}

impl GuideSettings {
    pub fn new(wpdb: Rc<dyn Wpdb>) -> GuideSettings {
        GuideSettings { wpdb }
    }

    pub fn value(&self, name: &str) -> Result<Option<Vec<u8>>, WpDbError> {
        // The current site's prefix and the table's name, so switch_to_blog() is followed.
        let table = self.wpdb.table_name("guide_settings");
        let statement = Query::table(&table)
            .select(&["value"])
            .where_eq("name", name)
            .limit(1)
            .build()?;
        Ok(match self.wpdb.query_statement(statement)? {
            QueryOutcome::Rows(rows) => rows.first().and_then(|row| row.get("value").cloned().flatten()),
            _ => None,
        })
    }
}
```

`name` goes to the database as a parameter, never as text, and a PHP callback on `query` still sees the statement. For WordPress's own tables, `wpdb.table_name("options")` gives the name `wpdb` uses now. A feature that needs a key-value or direct store asks the `EngineRegistry` for it by use, with `nosql()` or `direct()`.

## How to change this

- **Send the queries somewhere else:** register an `EngineFactory` for another scheme with the `EngineRegistry` and configure `default` with its URL, or build a `NativeWpdb` over any `SqlStore` (`WpDbParts`). The store must pass `speedyspec-data-conformance`'s SQL suite.
- **Give a Rust feature another `wpdb`:** implement `Wpdb` and pass it where the feature takes `Rc<dyn Wpdb>`. This replaces `wpdb` for that feature only; PHP's `$wpdb` stays `NativeWpdb`. <Ev test="speedyspec-wp-db-contracts::object_safe::wpdb_is_object_safe"/>
- **Change what one method does:** bind another handler under its key, such as `SpeedySpec\WpDb\QueryHandler` with `bind_command_handler::<Query>()`. The global `$wpdb` resolves each handler once and again only when its binding changes. This is a Rust binding: PHP has no adapter for the handlers. <Ev test="speedyspec-wp-db::messages::php_can_override"/>
- **Keep the request state somewhere else:** implement `WpdbState` in Rust, or `SpeedySpec\WpDb\WpdbState` in PHP wrapped in `PhpWpdbState`, and bind it under `SpeedySpec\WpDb\WpdbState`. The worker doesn't yet declare that key as a port PHP may bind, so for now the binding is made from Rust. <Ev test="speedyspec-wp-db-php::php::php_state_twin_replaces_memory"/>
- **Rewrite statements:** add a PHP or Rust callback to `query`, as in WordPress (it turns off the fast path), or a Rust callback to `speedyspec_query_statement`, which keeps it.
- **What must still pass:** the recorded scenarios (`compat/wp-db/scenarios.json`, replayed on MySQL, SQLite and PostgreSQL by `speedyspec-wp-db-php`'s replay tests) and WordPress's own database tests, except the breaks in `compat/wp-db/breaks.json` and the engine lists `compat/phpunit-sqlite.json` and `compat/phpunit-postgres.json`. <Ev test="speedyspec-wp-db-php::wordpress::wordpress_db_tests_pass"/> <Ev test="speedyspec-wp-db-php::wordpress::documented_breaks_are_listed"/>
- **Recording a new scenario:** add it to `compat/wp-db/scenarios.json` in speedyspec-server and run `cargo run -p speedyspec-compat -- record wp-db --wordpress 7.2-RC2` (the pin in `compat/wordpress.json`); a difference the port can't match goes in `breaks.json` with its reason.

## Post reading and the registries (native)

### Performance

A benchmark runs `get_post()` and `get_post_meta()` natively and on WordPress's own PHP, in the same embedded PHP over one MySQL database, timing the loops inside PHP. <Ev source="ss:crates/speedyspec-wp-posts-php/benches/read.rs#L1-L18" hash="d5e4a5cc2f244e75f14fca0c9f669e61e397f8a926c6d3f909e8160fb07d6081"/>

| Case | SpeedySpec | WordPress | Ratio |
|------|------------|-----------|-------|
| `get_post( 1 )`, warm cache | 0.94 µs | 0.92 µs | parity, within noise |
| `get_post( 1 )`, cold (`posts` group flushed) | 83 µs | 91 µs | a tie: MySQL decides it |
| `get_post_meta( 1, 'k', true )`, warm | 1.22 µs | 0.49 µs | 2.5× WordPress |

A warm `get_post()` lends the cached entry when it is plain and raw (exactly `WP_Post`'s 24 properties, scalars, `filter` `raw`): the use case answers the cache's own handle, PHP writes the entry's values once per request, and each call builds a new `WP_Post` from them, as WordPress's constructor does. The map of written entries is pruned of dropped entries only when it has doubled since the last prune (512 at least), so a loop over many live posts (a sitemap, an export, WP-CLI) stays amortized O(1) per read; a new request forgets what an earlier one left rather than releasing it. <Ev source="ss:crates/speedyspec-wp-posts-php/src/codec.rs#L53-L54" hash="b3377eba9cd617839fc409a5e1ac7753face5294f1ad4da128df7cbd28d7e848"/> <Ev source="ss:crates/speedyspec-wp-posts-php/src/codec.rs#L414-L415" hash="b59f9f29ff89558321aa4a984eb85c1dfc3ddff34830be00169eacd14a1c3495"/> <Ev source="ss:crates/speedyspec-wp-posts/src/read/get.rs#L258-L260" hash="63e67974ea2a1ea62fb077d86ddf78864370de2f27394af9fa88346d22d19b86"/> <Ev test="speedyspec-wp-posts-tests::read::warm_read_lends_the_cached_entry"/>

`get_post_meta()` is still 2.5× WordPress, about 0.7 µs a call. About 0.4 µs of it is in speedyspec-platform: speedyspec-wp-hooks-php resolves the hook store from the container on every store call, and speedyspec-php allocates the called function's name on every native call. Those are platform follow-ups; the posts and meta crates have no more to give there.

### Differences

- **Typed ids.** The Rust contract's id slices (`&[PostId]`) can't hold WordPress's `-1` or `"x"`. In PHP, `_prime_post_caches()` and `_prime_post_parent_id_caches()` run WordPress's `_validate_cache_id()`, which drops `"x"` as WordPress does, then also drop a negative id, which WordPress keeps in its `IN (…)` statement; `update_post_parent_caches()` reads a negative `post_parent` as its absolute value. No recorded scenario passes a negative id, so this is a documented difference here, not a `compat/posts-read/breaks.json` entry. <Ev source="ss:crates/speedyspec-wp-posts-php/src/read.rs#L914-L927" hash="fdf306efa0624233ec56c7d9226f2fc8e19536d61aa2e8d95603ca9dfb59d7c0"/> <Ev scenario="cache-prime-parent-ids" area="posts-read"/>

### Calling it from Rust

A Rust feature reads a post through `Posts`, which `PostsArea::api()` gives: the same use cases PHP's `get_post()` runs, with the `posts` cache group, its filters and the SQL table. <Ev source="ss:crates/speedyspec-wp-posts-php/src/lib.rs#L211-L213" hash="7623dcd547055871adea2d2f370b6cdc1445f00fa547a67f11dfc3867bc9dc74"/>

```rust
use speedyspec_wp_posts_contracts::{Filter, PostError, PostId, PostRef, Posts};

/// A published post's title, as `get_post( $id )->post_title` reads it, or `None` when there is no such post or it
/// isn't published.
fn published_title(posts: &dyn Posts, id: u64) -> Result<Option<Vec<u8>>, PostError> {
    // Read from the `posts` cache group, else with one `SELECT … WHERE ID = %d LIMIT 1`, cached for the next read.
    let Some(post) = posts.get(PostRef::Id(PostId(id)), Filter::Raw)? else {
        return Ok(None);
    };
    // `get_post_status()` runs its filter, so a plugin's answer counts, as in PHP.
    let published = posts
        .status(PostRef::Id(post.id))?
        .is_some_and(|status| status.as_str() == "publish");
    Ok(published.then_some(post.title))
}
```

`get` answers the raw post. For another context, sanitize in PHP or call `sanitize_post_field_word()` with the `Formatting` port. To let PHP rebind the read, send the message instead: `GetPost` through the query bus reaches whatever handler is bound at `SpeedySpec\WpPosts\GetPostHandler`.

### wp_insert_post()'s composed steps

`wp_insert_post()` is a Template Method: `Insert::run` calls nine steps in WordPress's order, and each step is a pure function over phase 2's rules or a call through a port. <Ev source="ss:crates/speedyspec-wp-posts/src/write/insert.rs#L1-L23" hash="f3b8467c868478a356e930dc2bfc54ddf78091d746f048932284479f32998a22"/> <Ev source="ss:crates/speedyspec-wp-posts/src/write/insert.rs#L255-L272" hash="8fd1a5bafe3ec808d81968eb7f4cd20acc980737400d0532cd55e7c840a839c3"/>

1. **`parse`**: the defaults, `wp_parse_args()`, `sanitize_post( 'db' )`, and the update case.
2. **`check_content`**: `wp_insert_post_empty_content`.
3. **`resolve`**: status, categories, the `pending` slug rule, `sanitize_title()`, `wp_resolve_post_date()` with `wp_checkdate` (phase 2's `resolve_post_date`) and `insert_post_dates`, comment and ping status, password, menu order and parent.
4. **`parent`**: `wp_insert_post_parent`, whose default callback breaks a loop through `wp_update_post()` (phase 2's `check_post_hierarchy_for_loops`).
5. **`slug`**: the trashed-slug suffixes, then `wp_unique_post_slug()` with its filters (phase 2's `unique_post_slug`, a Strategy per branch).
6. **`data`**: `$data`, the emoji check, `wp_insert_post_data` and `wp_unslash()`, mapped to a `PostRow` (Data Mapper).
7. **`write`**: `pre_post_update` and the repository's `update`, or the `import_id` check, `pre_post_insert` and `insert`.
8. **`after_write`**: the slug of a post written without one, terms, `meta_input`, the GUID, an attachment's file, the featured image and `clean_post_cache()`.
9. **`finish`**: `get_post()`, the page template, the transition, `edit_post`, `post_updated`, the `save_post` family and `wp_after_insert_post`, which share one object.

### Calling it from Rust

A Rust feature writes a post through `PostWritesApi`, which `PostsArea::writes()` gives: the same use case PHP's `wp_insert_post()` runs, with its hooks, its ports and the bound repository.

```rust
use speedyspec_php_serialize::{PhpKey, PhpValue};
use speedyspec_wp_posts::PostWritesApi;
use speedyspec_wp_posts_contracts::{PostError, PostId};

/// A draft with `title`, as `wp_insert_post( array( 'post_title' => $title ), true )` makes it: its id, or `None`
/// when WordPress answers a `WP_Error` (a callback refused it as empty, or the database rejected the row).
fn create_draft(writes: &PostWritesApi, title: &str) -> Result<Option<PostId>, PostError> {
    let postarr = PhpValue::Array(vec![
        (PhpKey::Str(b"post_title".to_vec()), PhpValue::Str(title.as_bytes().to_vec())),
        (PhpKey::Str(b"post_status".to_vec()), PhpValue::Str(b"draft".to_vec())),
    ]);
    // Every filter, action and statement runs in WordPress's order; `Err` is a failure WordPress would not hide.
    Ok(writes.wp_insert_post(postarr, true, true)?.ok())
}
```

To let PHP rebind the write, send `WpInsertPost` through the command bus instead; it reaches whatever handler is bound at `SpeedySpec\WpPosts\WpInsertPostHandler`.

### Review focus

Six rules need care when they change.

**Loose `==` in the lists.** `get_post_types()` and `get_post_stati()` match with PHP 8's `==` after `isset()`: `'public' => 1`, `'1'` and `'yes'` all match `public => true`; a null property never matches, even `'menu_position' => null`; empty arguments return everything whatever the operator; an unknown operator returns nothing. <Ev source="ss:crates/speedyspec-wp-posts/src/list.rs#L114-L121" hash="901c811955f72ed15726eddbc8090a5d2f0892b5373a6a656ec45428806c194c"/> <Ev test="speedyspec-wp-posts::recorded::list_scenarios_match_wordpress"/>

**`supports`.** `false` adds no features and keeps the property `false`; an empty array or null adds `title`, `editor` and `autosave` and keeps the property; a non-empty array adds its features and removes the property; `editor` adds `autosave` unless it is already supported. <Ev source="ss:crates/speedyspec-wp-posts/src/registry.rs#L116-L125" hash="2e1efeb6254bf829fa651933f21dd29f234ae8bac003d0ab04114dc70e8a9a6f"/> <Ev test="speedyspec-wp-posts::registry::supports_false_keeps_property_and_adds_nothing"/> <Ev test="speedyspec-wp-posts::registry::supports_empty_adds_defaults_and_keeps_property"/> <Ev test="speedyspec-wp-posts::registry::supports_list_removes_property"/> <Ev test="speedyspec-wp-posts::registry::editor_implies_autosave_unless_present"/>

**Registering again.** The new object replaces the old one in its original place; the old features stay, since nothing clears them; meta capabilities accumulate. <Ev test="speedyspec-wp-posts::registry::re_register_keeps_position_and_old_features"/> <Ev test="speedyspec-wp-posts::registry::re_register_accumulates_meta_caps"/>

**Unregistering rebuilds the meta capabilities.** As in WordPress 7.2, `unregister_post_type()` doesn't unset the type's own `$post_type_meta_caps` entries: it empties the map and rebuilds it from every remaining type whose `map_meta_cap` is truthy, in registration order. One custom capability can be owed to several types, so a capability another type still uses survives. `unregistration` takes the registered types and returns the whole rebuilt map, which the adapter assigns. <Ev source="ss:crates/speedyspec-wp-posts/src/registry.rs#L173-L183" hash="b265b980a5d751b8baeb322580d4b80abf755cc28086787612f7d83288e495f7"/> <Ev test="speedyspec-wp-posts::registry::unregister_keeps_meta_caps_another_type_still_owes"/> <Ev test="speedyspec-wp-posts::recorded::post_type_scenarios_match_wordpress"/>

**Names.** `sanitize_key()` runs before the length check, so `"Book Type!"` registers as `booktype`; `"0"` fails as `empty()`, as do `""` and 21 bytes. Statuses have no length check, so `register_post_status( '' )` stores `''`. An integer-like name (`"123"`) works and is keyed by its string in Rust. <Ev source="ss:crates/speedyspec-wp-posts/src/key.rs#L17-L25" hash="a442803b563e5cbdafec4743b197bb6db1721253fbe47563cfda95bcf9e3b34f"/> <Ev test="speedyspec-wp-posts::registry::integer_like_name_is_a_string_key"/> <Ev test="speedyspec-wp-posts::recorded::status_scenarios_match_wordpress"/>

**The rewrite context.** With neither `is_admin()` nor a permalink structure, `rewrite => true` stays `true`. With one, it becomes an array with `slug`, `with_front`, `pages`, `feeds` (forced to `has_archive` when that is falsy) and `ep_mask` (`permalink_epmask`, else `EP_PERMALINK`). <Ev test="speedyspec-wp-posts::recorded::set_props_matches_wordpress"/>

### Calling it from Rust

A runtime feature builds WordPress's initial post types into the two registries and asks for the public ones, as `get_post_types( array( 'public' => true ) )` does. The ports are the caller's: here the text seam's Rust `sanitize_title_with_dashes()` and a site with no permalink structure.

```rust
use speedyspec_php_serialize::{PhpKey, PhpValue};
use speedyspec_wp_posts::{
    InitialOptions, PostStatusRegistry, PostTypePorts, PostTypeRegistry, Untranslated,
    create_initial_post_types, post_type_names,
};
use speedyspec_wp_posts_contracts::{PostError, RewriteContext, TitleSanitizer};
use speedyspec_wp_text::title::{SanitizeContext, sanitize_title_with_dashes};

/// A site with no permalink structure, outside the admin: `rewrite` arguments stay as given.
struct PlainPermalinks;

impl RewriteContext for PlainPermalinks {
    fn rewrite_applies(&self) -> Result<bool, PostError> {
        Ok(false)
    }
}

/// `sanitize_title_with_dashes()`, from the text seam's Rust port.
struct TextTitles;

impl TitleSanitizer for TextTitles {
    fn sanitize_title_with_dashes(&self, title: &[u8]) -> Vec<u8> {
        sanitize_title_with_dashes(title, &SanitizeContext::Display)
    }
}

/// The names of the public post types WordPress registers on `init`: `post`, `page` and `attachment`. `Err` is a
/// port's failure (a translation or an option filter that throws), as WordPress's exception would stop the call.
fn public_post_types() -> Result<Vec<String>, PostError> {
    let mut types = PostTypeRegistry::new();
    let mut statuses = PostStatusRegistry::new();
    let ports = PostTypePorts {
        translator: &Untranslated,
        rewrite: &PlainPermalinks,
        titles: &TextTitles,
    };
    // Each registration also carries its actions and taxonomies; phase 4's adapter applies them.
    let _registrations =
        create_initial_post_types(&mut types, &mut statuses, &InitialOptions::default(), &ports)?;

    // get_post_types( array( 'public' => true ) ), compared with PHP 8's ==.
    let public = [(PhpKey::Str(b"public".to_vec()), PhpValue::Bool(true))];
    Ok(post_type_names(&types, &public, "and")
        .into_iter()
        .filter_map(|(_, name)| match name {
            PhpValue::Str(bytes) => String::from_utf8(bytes).ok(),
            _ => None,
        })
        .collect())
}
```

### The entity and its values

`Post` is one `wp_posts` row as a plain value: the 23 columns in table order, with each date pair as one `PostDate` (local and GMT). Its defaults are `WP_Post`'s property defaults. ### The ports

- **`PostRepository`**: `wp_posts`. Each method is one `$wpdb` statement that `post.php` makes, so query counts match WordPress: `find` (`WP_Post::get_instance()`'s `SELECT *`), `insert` (`wp_insert_post()`'s `$wpdb->insert`; since 0.4.0 it takes the filtered `$data` as a `PostRow` and answers a `WriteOutcome`) and the three slug-owner queries of `wp_unique_post_slug()`, one per branch. - **`PostReader`**: `get_post()`, through whatever cache the binding keeps. The rules read posts through it exactly where WordPress calls `get_post()`. `Uncached` is phase 2b's binding: it reads through `find`, and a zero ID is `None` with no statement, as `WP_Post::get_instance()` returns false before it queries. So phase 4 adds the cache by binding another reader, and the statements the rules make stay WordPress's.

### Patterns

- **Repository**, one statement per method: `PostRepository`, so a replay can compare statement sequences and an adapter can't merge or skip reads WordPress makes. `MemoryPostRepository` and phase 4's SQL repository implement it (**Strategy** per engine). <Ev source="ss:crates/speedyspec-wp-posts-memory/src/lib.rs#L1-L5" hash="4da557478296c6c525b3d3d1ee27edea888be55d3b76287a4a1fca385c07c808"/>
- **Data Mapper**: `PostMapper`, so the entity knows nothing of rows or cache entries. <Ev test="speedyspec-wp-posts-sql::mapper::rows_map_to_the_cached_object"/>
- **Strategy ports**: `Clock`, `SlugTruncation`, `BadSlugs` and `PostReader`, each a place where phase 4 or 5 binds WordPress's PHP or a Rust adapter.
- **Adapter**: `Uncached`, from repository to reader. <Ev source="ss:crates/speedyspec-wp-posts/src/reader.rs#L5-L19" hash="09da15425c05c61578f330c352c0763b5ac7394e30c22dffec7fbfac1012ace4"/>
- **Value Object**: `Post`, `PostId`, `PostDateTime`, `PostDate`, `Slug` and the rest.

### Review focus

**Statements are part of the answer.** Each replay compares the result and the `$wpdb` statements in order, so a rule that reads a post once more or once less than WordPress fails. `get_page_uri()` reads every ancestor, then each one again for its name, because WordPress does. <Ev source="ss:crates/speedyspec-wp-posts/src/hierarchy.rs#L162-L176" hash="9580e160ea1319a8723ac2909f28debb657df6f121321ba350f8604abfa13701"/> <Ev test="speedyspec-wp-posts::entity::hierarchy_matches_wordpress"/>

**PHP truth of a slug owner.** The owner queries answer a name, and an owner named `""` or `"0"` is false in PHP, so it never forces a suffix. <Ev source="ss:crates/speedyspec-wp-posts/src/slug.rs#L99-L103" hash="225bf09dd80cfbaff5903a3bab161af7184503ad22e76f4ac47e4fbefd7194d6"/> <Ev test="speedyspec-wp-posts::entity::slug_scenarios_match_wordpress"/>

**PCRE's `$`.** `/^[0-9]+$/` and the pagination pattern match before one final newline, so `"5\n"` counts as a number and `"2\n"` as a page number. <Ev source="ss:crates/speedyspec-wp-posts/src/slug.rs#L134-L159" hash="58aa3c6b10b4dc4a44d103c50c03f63afc56c5c969dd7d47a186977912fa2477"/> <Ev test="speedyspec-wp-posts::entity::slug_scenarios_match_wordpress"/>

**The date-archive test.** In the flat branch, a `post` slug that is a non-zero number conflicts when `%postname%` comes first in the permalink structure, or after `%year%` (below 13) or `%monthnum%` (below 32), unless it is the post's own name. <Ev source="ss:crates/speedyspec-wp-posts/src/slug.rs#L166-L199" hash="cf971bc8bac6f407f966b2d60da82db5a4846e13a40362bb831d05fb79739e0b"/>

**The clock.** `wp_resolve_post_date()` reads now only when both dates are empty. The replay's clock fails if a rule asks for now where WordPress didn't. <Ev test="speedyspec-wp-posts::entity::clock_refuses_now_where_none_was_recorded"/> <Ev test="speedyspec-wp-posts::entity::dates_match_wordpress"/>

**Loops.** `wp_find_hierarchy_loop()`'s tortoise and hare reads parents in PHP's order, and the members come back in WordPress's key order. `check_post_hierarchy_for_loops` returns the members it would detach (`break_loop`) and writes nothing. <Ev source="ss:crates/speedyspec-wp-posts/src/hierarchy.rs#L42-L140" hash="65cbd06c5e1fa7f7a58c04bb3229f7a8f583f1d56832bc82d5f79bedfd74f785"/>

### Calling it from Rust

A runtime feature seeds an in-memory `wp_posts`, asks for a free slug as `wp_unique_post_slug()` does, and builds a page's URI as `get_page_uri()` does. Truncation is the text seam's Rust `wp_truncate_slug()`; no post type is registered, so `post` and `page` both take the flat branch.

```rust
use speedyspec_wp_posts::{
    NoBadSlugs, PostTypeRegistry, SlugContext, SlugPorts, SlugRequest, Uncached, page_uri,
    unique_post_slug,
};
use speedyspec_wp_posts_contracts::{
    Post, PostError, PostId, PostParent, PostReader, PostRepository, PostRow, PostTypeName,
    RowValue, Slug, SlugTruncation,
};
use speedyspec_wp_posts_memory::MemoryPostRepository;
use speedyspec_wp_text::helpers::wp_truncate_slug;

/// `wp_truncate_slug()`, from the text seam's Rust port.
struct TextTruncation;

impl SlugTruncation for TextTruncation {
    fn truncate(&self, slug: &[u8], length: usize) -> Vec<u8> {
        wp_truncate_slug(slug, i64::try_from(length).unwrap_or(i64::MAX))
    }
}

/// A page row with an explicit ID.
fn page(id: u64, parent: u64, name: &str) -> Post {
    Post {
        id: PostId(id),
        parent: PostParent::from(PostId(parent)),
        name: Slug::from(name),
        post_type: PostTypeName::new("page"),
        ..Post::default()
    }
}

/// Writes `post` with its own ID, as `wp_insert_post()` does for a free `import_id`.
fn seed(posts: &MemoryPostRepository, post: &Post) -> Result<(), PostError> {
    let id = i64::try_from(post.id.0).unwrap_or(i64::MAX);
    posts.insert(&PostRow::from_post(post).with("ID", RowValue::Int(id)))?;
    Ok(())
}

/// `hello-world-2` for a new post, and `about/team` for page 11.
fn slug_and_uri() -> Result<(Vec<u8>, Vec<u8>), PostError> {
    let posts = MemoryPostRepository::new();
    seed(&posts, &Post {
        id: PostId(1),
        name: Slug::from("hello-world"),
        ..Post::default()
    })?;
    seed(&posts, &page(10, 0, "about"))?;
    seed(&posts, &page(11, 10, "team"))?;
    let reader = Uncached(&posts);

    // wp_unique_post_slug( 'hello-world', 0, 'publish', 'post', 0 ), with no filters.
    let types = PostTypeRegistry::new();
    let ports = SlugPorts {
        repository: &posts,
        posts: &reader,
        types: &types,
        truncation: &TextTruncation,
        bad: &NoBadSlugs,
    };
    let context = SlugContext {
        feeds: vec![b"feed".to_vec(), b"rss2".to_vec()],
        pagination_base: b"page".to_vec(),
        permalink_structure: b"/%postname%/".to_vec(),
    };
    let request = SlugRequest {
        slug: b"hello-world",
        post_id: PostId(0),
        status: "publish",
        post_type: "post",
        parent: PostParent::NONE,
    };
    let slug = unique_post_slug(&request, &context, &ports)?;

    // get_page_uri( 11 ), before its filter.
    let uri = match reader.post(PostId(11))? {
        Some(team) => page_uri(&reader, &team)?,
        None => Vec::new(),
    };
    Ok((slug, uri))
}
```
