## Behaviour

Served by WordPress's PHP; the Rust rules below are not wired yet. The runtime worker links neither posts crate, so PHP on SpeedySpec runs WordPress's own `post.php` until phase 4 of the posts and meta port. <Ev source="ss:crates/speedyspec-php-runtime/Cargo.toml#L20-L55" hash="955f1ccec24cc11da3fa0826db96868561c6e6c3cdc55277b37b80c09b513508"/>

## The Rust rules

`check_post_type_name` is the name rule: `sanitize_key()` without its filter, then `NameLength` when the result is PHP-`empty()` (`""` or `"0"`) or longer than 20 bytes. `"Book Type!"` registers as `booktype`, and an integer-like name such as `"123"` works. The error carries WordPress's code and message, and `NAME_LENGTH_VERSION` is the `_doing_it_wrong()` version, `4.2.0`. <Ev source="ss:crates/speedyspec-wp-posts/src/key.rs#L5-L25" hash="a756000485a6717c3dd4fd670d87843a41c45924a39f3f78172c440ab66c2465"/> <Ev test="speedyspec-wp-posts-contracts::values::errors_carry_wordpress_codes_and_messages"/>

`PostTypeRegistry::register` is the rest: it builds the object as `new WP_Post_Type()` does (`resolve_post_type`), remembers its meta capabilities, runs `add_supports()`, stores it (in its old place when the name is already registered), and returns the actions and taxonomies for the adapter: `add_meta_boxes_{$post_type}` when `register_meta_box_cb` is set, `future_{$post_type}`, and each value of an array `taxonomies`. <Ev source="ss:crates/speedyspec-wp-posts/src/registry.rs#L226-L234" hash="b57142023dbe6972237ca930455c55b16b3a56941a123b92bc9ca1b180fb3e99"/> <Ev source="ss:crates/speedyspec-wp-posts/src/registry.rs#L55-L66" hash="1628bea29c8386281db8dc045967aaab7076600cc91c3c6acb30fde15a7fd304"/>

The 11 recorded post type scenarios (33 calls, 18 of them `register_post_type()`) replay as in WordPress 7.1.5: each call's result, `_doing_it_wrong()` messages, actions added and removed, taxonomies and `$post_type_meta_caps`, and the whole of `$wp_post_types`, `$_wp_post_type_features` and `$wp_post_statuses` at the end. They cover bad names, each form of `supports`, a meta box callback, taxonomies, registering again and unregistering. <Ev test="speedyspec-wp-posts::recorded::post_type_scenarios_match_wordpress"/> <Ev test="speedyspec-wp-posts::registry::re_register_keeps_position_and_old_features"/> <Ev test="speedyspec-wp-posts::registry::integer_like_name_is_a_string_key"/>

## Limits

- Recorded from WordPress 7.1.5 under the recorder's stubs: `__()` and `_x()` return their text, the rewrite functions do nothing, `register_taxonomy_for_object_type()` only notes its call, and `get_object_taxonomies()` returns nothing. <Ev source="ss:compat/posts/record.php#L49-L62" hash="6398e7220fdfb100a72b707de8a1729a005479e3dd92f38f53c6da72f86a0d8d"/>
- The `register_post_type_args`, `register_{$post_type}_post_type_args` and `post_type_labels_{$post_type}` filters, and the `registered_post_type` actions, run only in phase 4. The rules return what WordPress computes with no callback added.
- `$args` must be an array. The query-string form `wp_parse_args()` accepts is the adapter's to parse.
- The rewrite rules, permastructs and query vars it adds belong to the rewrite seam.
- Unrecorded approximations: a non-array `capabilities` counts as empty, where PHP throws in `array_merge()`; an array `capability_type` missing index 0 or 1 gives `""` in the capability names; a non-empty `supports` that is neither an array nor an object adds no features. <Ev source="ss:crates/speedyspec-wp-posts/src/post_type.rs#L8-L16" hash="16d705e34605f277b0ce21a2867ff9b05605ce89c0bb79df47ed7016db112ba3"/> <Ev source="ss:crates/speedyspec-wp-posts/src/registry.rs#L15-L20" hash="3f21624b9e78384879a0d57e6539b32090986f56f53e4e31e8a71100e89ddf91"/>
