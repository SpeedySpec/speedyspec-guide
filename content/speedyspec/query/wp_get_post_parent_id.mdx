## Behaviour

Served by WordPress's PHP; the Rust rules below are not wired yet. The runtime worker links no posts crate, so PHP on SpeedySpec runs WordPress's own `post.php` until phase 4 of the posts and meta port. <Ev source="ss:crates/speedyspec-php-runtime/Cargo.toml#L24-L60" hash="4e45d1d171d753b4dfe1c47e78d7b37982c3572c9fc8cf407854fed9c53b58e9"/>

## The Rust rule

`post_parent_id` reads the post through the `PostReader` port and answers its `post_parent` (0 for none), or `None` (false) for a missing post. <Ev source="ss:crates/speedyspec-wp-posts/src/hierarchy.rs#L12-L15" hash="55ea644740999194bba792e11750ccd63aa2ebbf6b648bc76bb013e97235b13d"/>

The 3 recorded calls (a parent, none, a missing post) replay as in WordPress 7.2-RC2, comparing the result and the posts read. <Ev test="speedyspec-wp-posts::entity::hierarchy_matches_wordpress"/> <Ev source="ss:compat/posts-entity/record.php#L634-L671" hash="6f47b85147282bdf090f33ec9af0e325f028a7ac61bc8eb02647a03f03402cde"/>

## Limits

- `get_post()` given 0 or null falls back to the global `$post` in WordPress; `Uncached` answers none, and phase 5 decides where that fallback lives.
- The rule takes a post ID; the adapter reads a `WP_Post` argument's ID.
- `Uncached` reads every post through `find`, as WordPress does with no object cache; phase 4's reader reads the `posts` cache group first. <Ev source="ss:crates/speedyspec-wp-posts/src/reader.rs#L5-L19" hash="09da15425c05c61578f330c352c0763b5ac7394e30c22dffec7fbfac1012ace4"/>
- Recorded from WordPress 7.2-RC2 behind the recorder's stub `$wpdb`, which answers only the statements `PostRepository` mirrors and compares strings byte for byte. MySQL's `_ci` collations ignore case and trailing spaces, so rows that differ only so are not proven; the SQL repository (phase 4) decides. <Ev source="ss:compat/posts-entity/record.php#L133-L137" hash="582625381c482b18c1cd564398a320d093d272f1212981bd5dec09dfd0828f01"/>
