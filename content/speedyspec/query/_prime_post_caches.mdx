## Differences

- **The meta statement.** This function reads post meta through the native meta functions, whose `update_meta_cache()` statement selects `meta_id` too (`SELECT meta_id, post_id, meta_key, meta_value …`, where WordPress sends `SELECT post_id, meta_key, meta_value …`), because the meta entity carries its id. A plugin that matches the exact text in a `query` filter misses it; the rows, the cache and the query count are WordPress's. It is the meta seam's documented difference, recorded here as a break on the scenarios that watch the statement. <Ev break="cache-prime-statement" step="1" area="posts-read"/> <Ev break="count-readable-statement" step="1" area="posts-read"/> <Ev source="ss:compat/posts-read/breaks.json#L1-L14" hash="c5f076b4794a20681d8b985e4d9fb2e12e1bda0c5f3b95a2ba59b4e080731c8d"/> See [update_meta_cache()](/speedyspec/meta/update_meta_cache/).
- **Typed ids.** The use case takes `&[PostId]`, which can hold neither WordPress's `-1` nor `"x"`. The PHP function runs WordPress's own `_validate_cache_id()` first, which drops `"x"` with `_doing_it_wrong()` as in WordPress, then also drops a negative id, which WordPress keeps: its `IN (…)` statement holds `-1`, and SpeedySpec's leaves it out. No row has a negative id, so the rows and the cache are the same; only the statement a `query` filter sees differs. The recorded `cache-prime-parent-ids` scenario passes `"x"` and `-1` and replays exactly. The meta and term steps still take the ids as given, as WordPress passes them its unfiltered `$ids`: `update_postmeta_cache()` reads each through `intval`, a negative one as 0. <Ev source="ss:crates/speedyspec-wp-posts-php/src/read.rs#L893-L906" hash="f1b45a5ee917a39d09b9342c54e6792b4d6567d360771e5552674ac9e70a7b50"/> <Ev source="ss:crates/speedyspec-wp-posts/src/read/cache.rs#L218-L228" hash="10663d285c1cccd689c288ae395e0c10580da9a463f26d2516eebe560810f63a"/> <Ev scenario="cache-prime-parent-ids" area="posts-read"/>
