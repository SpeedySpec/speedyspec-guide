## Behaviour

Served by WordPress's PHP; the Rust rules below are not wired yet. The runtime worker links neither posts crate, so PHP on SpeedySpec runs WordPress's own `post.php` until phase 4 of the posts and meta port. <Ev source="ss:crates/speedyspec-php-runtime/Cargo.toml#L20-L55" hash="955f1ccec24cc11da3fa0826db96868561c6e6c3cdc55277b37b80c09b513508"/>

## The Rust rules

`post_stati` (objects) and `post_status_names` (names) filter the `PostStatuses` port's list with the same `filter_object_list` as `get_post_types()`. An argument matches when the object has the property (`isset()`) and it is loosely equal, by PHP 8's `==`, to the wanted value: `'public' => 1`, `'1'` and `'yes'` all match `public => true`, and a null property never matches. Empty arguments return every entry whatever the operator; an unknown operator returns none. <Ev source="ss:crates/speedyspec-wp-posts/src/list.rs#L166-L185" hash="1cb39adcc2fba3db80e9af476758a3d26bef5ab45d6560fb748ea745eaaed86b"/>

The 4 recorded calls in the `lists` scenario and 4 after `create_initial_post_types()` replay as in WordPress 7.1.5. <Ev test="speedyspec-wp-posts::recorded::list_scenarios_match_wordpress"/> <Ev test="speedyspec-wp-posts::recorded::initial_post_types_match_wordpress"/>
