## The Rust rule

`check_post_hierarchy_for_loops` is the `wp_insert_post_parent` filter's callback without its writes. No parent stays 0; a new post (ID 0) keeps its parent; a post can't be its own parent. Otherwise it runs `find_hierarchy_loop` from the post with the new parent standing in for its own. No loop keeps the parent; a loop through the post drops the parent to 0; a loop that doesn't contain the post keeps the parent and returns the loop's members as `break_loop`, in `wp_find_hierarchy_loop()`'s order. WordPress detaches each member with `wp_update_post( array( 'ID' => $member, 'post_parent' => 0 ) )`; phase 5 runs those calls. <Ev source="ss:crates/speedyspec-wp-posts/src/hierarchy.rs#L92-L134" hash="079a83357a644e70d22a51ebd200f0c4cd585ec44f969508664afb0189bd9c7b"/>

The 6 recorded calls replay as in WordPress 7.2-RC2, comparing the result and the posts read, in order. <Ev test="speedyspec-wp-posts::entity::hierarchy_matches_wordpress"/> <Ev source="ss:compat/posts-entity/record.php#L634-L671" hash="6f47b85147282bdf090f33ec9af0e325f028a7ac61bc8eb02647a03f03402cde"/>

## Limits

- No recorded call meets a loop that leaves the post out, since WordPress would then write to the table. `break_loop` is proven by unit tests only.
- The `wp_insert_post_parent` filter and the `wp_update_post()` calls are phase 5's, inside `wp_insert_post()`, before the slug step.
- Negative parents: WordPress keeps `(int) $postarr['post_parent']` as it is, and `PostId` can't hold a negative number. Phase 5 decides how to clamp it.
- `Uncached` reads every post through `find`, as WordPress does with no object cache; phase 4's reader reads the `posts` cache group first. <Ev source="ss:crates/speedyspec-wp-posts/src/reader.rs#L5-L19" hash="09da15425c05c61578f330c352c0763b5ac7394e30c22dffec7fbfac1012ace4"/>
- Recorded from WordPress 7.2-RC2 behind the recorder's stub `$wpdb`, which answers only the statements `PostRepository` mirrors and compares strings byte for byte. MySQL's `_ci` collations ignore case and trailing spaces, so rows that differ only so are not proven; the SQL repository (phase 4) decides. <Ev source="ss:compat/posts-entity/record.php#L133-L137" hash="582625381c482b18c1cd564398a320d093d272f1212981bd5dec09dfd0828f01"/>
