## Behaviour

Served by WordPress's PHP; the Rust rules below are not wired yet. The runtime worker links neither posts crate, so PHP on SpeedySpec runs WordPress's own `post.php` until phase 4 of the posts and meta port. <Ev source="ss:crates/speedyspec-php-runtime/Cargo.toml#L20-L55" hash="955f1ccec24cc11da3fa0826db96868561c6e6c3cdc55277b37b80c09b513508"/>

## The Rust rule

`PostTypes::post_type` is the lookup: one registered post type, as an owned `PostType` whose properties are the object's `get_object_vars()`, in order. `PostTypeRegistry` answers it from memory; phase 4's adapter reads `$wp_post_types` live. <Ev source="ss:crates/speedyspec-wp-posts-contracts/src/ports.rs#L25-L31" hash="c1960a37a7fc775ee14b766a1f30198cb356e6e115af07b588eb082cd54b7c45"/> <Ev source="ss:crates/speedyspec-wp-posts-contracts/src/values.rs#L105-L111" hash="933246bb03fd9df9d5e260fbeddaeeac4ad6d9546a90914d34dbdbed12b2a085"/>

No recording calls `get_post_type_object()` itself. Every post type scenario compares the whole `$wp_post_types` it reads from, object by object and property by property. <Ev test="speedyspec-wp-posts::recorded::post_type_scenarios_match_wordpress"/> <Ev test="speedyspec-wp-posts-contracts::values::post_type_to_php_is_a_wp_post_type_object"/>

## Limits

- Recorded from WordPress 7.2-RC2 under the recorder's stubs: `__()` and `_x()` return their text, the rewrite functions do nothing, `register_taxonomy_for_object_type()` only notes its call, and `get_object_taxonomies()` returns nothing. <Ev source="ss:compat/posts/record.php#L53-L66" hash="6398e7220fdfb100a72b707de8a1729a005479e3dd92f38f53c6da72f86a0d8d"/>
- The `! is_scalar()` check on the name is the adapter's: the port takes a UTF-8 name.
