## Behaviour

Native: `post.php`'s `get_post_status()` is a line of PHP over `SpeedySpec\WpPosts\Native\get_post_status`, which dispatches the `GetPostStatus` message to the handler bound at `SpeedySpec\WpPosts\GetPostStatusHandler`, so a handler PHP binds there takes the call. <Ev source="ss:crates/speedyspec-wp-posts-php/src/posts.php#L45-L48" hash="51738213115c0a41cf9d804b1ab9e564b2396006803328eca1b74120a33e6850"/> <Ev source="ss:crates/speedyspec-wp-posts/src/read/get.rs#L390-L398" hash="a951340b5a83688bb6df36702f197ec5c9795915ea8c55dc514036a7da34d095"/> <Ev source="ss:crates/speedyspec-wp-posts-php/src/read.rs#L495-L520" hash="8f94b124544723a5fe795c878d6bcbec3a5c97c19163c934fd3f3b914c75f0ce"/>

It reads the post and follows WordPress's branches: `inherit` attachments take their parent's status (a trashed parent's `_wp_trash_meta_status`, else `publish` for a missing parent), an attachment's own status otherwise, then the `get_post_status` filter with `( $post_status, $post )`. With a trashed parent it reads the parent's status twice, as WordPress does. A `WP_Post` given explicitly with `filter` `sample` is used as it is; with no argument, a `sample` global is read again by its id, as on WordPress's edit screen. <Ev scenario="status-each" area="posts-read"/> <Ev scenario="status-missing" area="posts-read"/> <Ev scenario="status-global" area="posts-read"/> <Ev scenario="status-attachment-inherit" area="posts-read"/> <Ev scenario="status-attachment-parent-trash" area="posts-read"/> <Ev scenario="status-attachment-parent-trash-no-meta" area="posts-read"/> <Ev scenario="status-attachment-own" area="posts-read"/> <Ev scenario="status-sample" area="posts-read"/> <Ev scenario="status-filter" area="posts-read"/> <Ev scenario="ms-get-single" area="posts-read"/> <Ev test="speedyspec-wp-posts-php::compat::main"/> <Ev test="speedyspec-wp-posts-tests::read::status_follows_a_trashed_parent"/>

WordPress's own `Tests_Post_GetPostStatus` tests, copied from 7.2-RC2, call it and pass against the port on a single site and on multisite. <Ev test="speedyspec-wp-posts-php::wordpress::wordpress_posts_runs_pass"/>

The `update_meta_cache()` statement it triggers is WordPress's own text, `SELECT post_id, meta_key, meta_value …`, which the `cache-prime-statement` scenario checks. <Ev scenario="cache-prime-statement" area="posts-read"/>

## Differences

- **An object argument is read as a copy.** The readers beside `get_post()` hand an object argument to the use case as a copy, for one dispatch. WordPress's `get_post()` inside them sanitizes a `stdClass` with no `filter` in place, setting `filter` to `raw` and casting its ids to int; on SpeedySpec the caller's object is left as it was. The answer is the same. Not recorded. <Ev source="ss:crates/speedyspec-wp-posts-php/src/read.rs#L30-L34" hash="2bc082f37a3aa63398531ebb37534e185fe71501b2fbacd16834877684966948"/>
- **Objects in hook arguments are copies.** The use cases carry PHP values, and `PhpValueHooks` makes them PHP values on the way into a hook, so a callback gets an equal object of the same class, not the one WordPress would hand it. An object a callback returns crosses back as it is (a `stdClass` as an equal copy).
