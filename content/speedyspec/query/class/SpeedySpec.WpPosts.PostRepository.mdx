## Behaviour

The PHP twin of the `PostRepository` port: `wp_posts`, with a method per `$wpdb` call `post.php` makes, and `engine`.

- **Reads:** `find`, `find_many`, `parent_ids`, `pages_by_names`, `all_page_ids`, `count_by_status`, `count_attachments`, `last_post_time`, `available_mime_types` and the three slug owners (`attachment_slug_owner`, `hierarchical_slug_owner`, `flat_slug_owner`).
- **Writes `wp_insert_post()` and `set_post_type()` make:** `insert( $row )` and `update( $id, $row )`, each given exactly the `wp_insert_post_data`-filtered `$data` (with `ID` when a free `import_id` set it); `import_id_taken`, `raw_row`, `update_name`, `update_guid` and `update_post_type`.
- **For the 5b writers:** `update_status`, `update_pinged`, `children_of_type`, `reparent_children`, `revision_ids`, `reparent_attachments`, `remove` and `auto_drafts_older_than_a_week`.

Values cross as PHP holds them: a post is a row array keyed by column, as `$wpdb->get_row( …, ARRAY_A )` gives it; ids are ints, names and types strings, and "nothing" is `null`. `insert()` answers the new id; `update()` and the other writes answer the rows changed. ## Override

Bind an object implementing it at `SpeedySpec\WpPosts\PostRepository` in the container. The use cases resolve the port on every call, so the binding applies for its request; a binding that throws, or an object that doesn't implement the interface, is an `Error` from the post function, and nothing falls back to SQL.
