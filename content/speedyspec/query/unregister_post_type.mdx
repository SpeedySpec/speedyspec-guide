## Behaviour

Native: `post.php`'s `unregister_post_type()` is a line of PHP over `SpeedySpec\WpPosts\Native\unregister_post_type`. <Ev source="ss:crates/speedyspec-wp-posts-php/src/post-types.php#L54-L57" hash="d135826de1f4001fb69e01581ead4de2474c64b2d52c4079caffd620c0eba485"/> <Ev source="ss:crates/speedyspec-wp-posts-php/src/registry.rs#L416-L463" hash="340ebc1ed971a244591a9ee134d68a5dfd20330cd088719f4b4b680578910239"/>

It refuses a built-in or missing type, calls the class's own removal methods, unsets the type with the caller's key, rebuilds `$post_type_meta_caps` from the live types left, and fires `unregistered_post_type`. <Ev scenario="types-unregister" area="posts-read"/> <Ev test="speedyspec-wp-posts-php::registry::main"/> <Ev test="speedyspec-wp-posts-php::registry::main"/>

The registries have no handler in the container: they are PHP's globals (`$wp_post_types`, `$wp_post_statuses`, `$_wp_post_type_features`), read and written live, so a handler would only wrap the global and there is nothing to rebind. Change a registration with WordPress's own hooks. <Ev source="ss:crates/speedyspec-wp-posts-php/src/lib.rs#L27-L34" hash="cee2b8bc56cdb2f3c4038d6df9b3cd87ec0268ee2f97be22e1d5ff45d3187848"/>

WordPress's own `Tests_Post_IsPostTypeViewable`, `Tests_Post_Types` tests, copied from 7.2-RC2, call it and pass against the port on a single site and on multisite. <Ev test="speedyspec-wp-posts-php::wordpress::wordpress_posts_runs_pass"/>

## The Rust rules

`PostTypeRegistry::unregister` gives `Invalid` (`invalid_post_type`, "Invalid post type.") for a missing type and `Builtin` (the same code, "Unregistering a built-in post type is not allowed", with no full stop, as in 7.2-RC2) when its `_builtin` is truthy. Otherwise `unregistration` names what to remove, the type's entry in `$_wp_post_type_features` and the `add_meta_boxes_{$post_type}` and `future_{$post_type}` actions, and returns `$post_type_meta_caps` rebuilt as WordPress 7.2 rebuilds it: emptied, then filled from the `cap` of every remaining type whose `map_meta_cap` is truthy, in registration order. A custom capability another type still owes survives. <Ev source="ss:crates/speedyspec-wp-posts/src/registry.rs#L173-L183" hash="b265b980a5d751b8baeb322580d4b80abf755cc28086787612f7d83288e495f7"/> <Ev source="ss:crates/speedyspec-wp-posts/src/registry.rs#L320-L331" hash="dc6d00703db13a829a3810f6b00e14b20b015eee8218e53575865775f715e453"/> <Ev source="ss:crates/speedyspec-wp-posts-contracts/src/error.rs#L9-L40" hash="8c56a8b592fd60e3df1df535299bdd1ae5347b8464df2a467f7f219d159394eb"/>

The recorded `unregister` and `unregister-shared-caps` scenarios replay as in WordPress 7.2-RC2, call by call, with `$post_type_meta_caps` after each. In the second, two types share a capability type: the shared capabilities stay after the first goes, and the map is empty after the second. <Ev test="speedyspec-wp-posts::registry::unregister_keeps_meta_caps_another_type_still_owes"/> <Ev test="speedyspec-wp-posts::recorded::post_type_scenarios_match_wordpress"/> <Ev test="speedyspec-wp-posts::registry::unregister_removes_features_and_meta_caps"/> <Ev test="speedyspec-wp-posts::registry::unregister_builtin_is_refused"/> <Ev test="speedyspec-wp-posts::registry::unregister_missing_is_invalid"/>
