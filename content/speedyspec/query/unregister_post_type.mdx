## Behaviour

Served by WordPress's PHP; the Rust rules below are not wired yet. The runtime worker links neither posts crate, so PHP on SpeedySpec runs WordPress's own `post.php` until phase 4 of the posts and meta port. <Ev source="ss:crates/speedyspec-php-runtime/Cargo.toml#L24-L60" hash="4e45d1d171d753b4dfe1c47e78d7b37982c3572c9fc8cf407854fed9c53b58e9"/>

## The Rust rules

`PostTypeRegistry::unregister` gives `Invalid` (`invalid_post_type`, "Invalid post type.") for a missing type and `Builtin` (the same code, "Unregistering a built-in post type is not allowed", with no full stop, as in 7.2-RC2) when its `_builtin` is truthy. Otherwise `unregistration` names what to remove, the type's entry in `$_wp_post_type_features` and the `add_meta_boxes_{$post_type}` and `future_{$post_type}` actions, and returns `$post_type_meta_caps` rebuilt as WordPress 7.2 rebuilds it: emptied, then filled from the `cap` of every remaining type whose `map_meta_cap` is truthy, in registration order. A custom capability another type still owes survives. <Ev source="ss:crates/speedyspec-wp-posts/src/registry.rs#L169-L179" hash="b265b980a5d751b8baeb322580d4b80abf755cc28086787612f7d83288e495f7"/> <Ev source="ss:crates/speedyspec-wp-posts/src/registry.rs#L297-L308" hash="dc6d00703db13a829a3810f6b00e14b20b015eee8218e53575865775f715e453"/> <Ev source="ss:crates/speedyspec-wp-posts-contracts/src/error.rs#L5-L36" hash="8c56a8b592fd60e3df1df535299bdd1ae5347b8464df2a467f7f219d159394eb"/>

The recorded `unregister` and `unregister-shared-caps` scenarios replay as in WordPress 7.2-RC2, call by call, with `$post_type_meta_caps` after each. In the second, two types share a capability type: the shared capabilities stay after the first goes, and the map is empty after the second. <Ev test="speedyspec-wp-posts::registry::unregister_keeps_meta_caps_another_type_still_owes"/> <Ev test="speedyspec-wp-posts::recorded::post_type_scenarios_match_wordpress"/> <Ev test="speedyspec-wp-posts::registry::unregister_removes_features_and_meta_caps"/> <Ev test="speedyspec-wp-posts::registry::unregister_builtin_is_refused"/> <Ev test="speedyspec-wp-posts::registry::unregister_missing_is_invalid"/>

## Limits

- Recorded from WordPress 7.2-RC2 under the recorder's stubs: `__()` and `_x()` return their text, the rewrite functions do nothing, `register_taxonomy_for_object_type()` only notes its call, and `get_object_taxonomies()` returns nothing. <Ev source="ss:compat/posts/record.php#L53-L66" hash="6398e7220fdfb100a72b707de8a1729a005479e3dd92f38f53c6da72f86a0d8d"/>
- Removing the type from its taxonomies is the adapter's, in phase 4. The recorder's `get_object_taxonomies()` returns nothing, so no recording covers it.
- Removing rewrite rules, permastructs and the query var belongs to the rewrite seam. The `unregistered_post_type` action runs only in phase 4.
