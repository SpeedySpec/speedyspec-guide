## Behaviour

Served by WordPress's PHP; the Rust rules below are not wired yet. The runtime worker links neither posts crate, so PHP on SpeedySpec runs WordPress's own `post.php` until phase 4 of the posts and meta port. <Ev source="ss:crates/speedyspec-php-runtime/Cargo.toml#L20-L55" hash="955f1ccec24cc11da3fa0826db96868561c6e6c3cdc55277b37b80c09b513508"/>

## The Rust rule

`is_post_type_viewable` is `publicly_queryable || ( _builtin && public )`, by PHP truth, for a `PostType`; `post_type_name_viewable` looks the name up first and is false for a missing type. <Ev source="ss:crates/speedyspec-wp-posts/src/queries.rs#L36-L39" hash="18690468575cfab6e8ec480b4aef9b8308eb9264a545c2c1b3401ba952e1d552"/> <Ev source="ss:crates/speedyspec-wp-posts/src/queries.rs#L50-L55" hash="8009733c8cadc0d9f1f7964c9d55f038db4b6e03ce55a70a573fe11e53f0458b"/>

The 8 recorded calls in the `lists` scenario and 32 after `create_initial_post_types()` replay as in WordPress 7.1.5. <Ev test="speedyspec-wp-posts::recorded::list_scenarios_match_wordpress"/> <Ev test="speedyspec-wp-posts::recorded::initial_post_types_match_wordpress"/>

## Limits

- Recorded from WordPress 7.1.5 under the recorder's stubs: `__()` and `_x()` return their text, the rewrite functions do nothing, `register_taxonomy_for_object_type()` only notes its call, and `get_object_taxonomies()` returns nothing. <Ev source="ss:compat/posts/record.php#L49-L62" hash="6398e7220fdfb100a72b707de8a1729a005479e3dd92f38f53c6da72f86a0d8d"/>
- The `is_post_type_viewable` filter and its `true ===` check run only in phase 4; the rule gives the value passed to it.
- The `is_scalar()` check on a name is the adapter's.
