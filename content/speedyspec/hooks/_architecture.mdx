## The domain and its port

`speedyspec-wp-hooks` is `plugin.php` and `WP_Hook` in Rust: `HookApi` holds every function, `WpHook` is `WP_Hook` ported literally (with how running iterations follow changes, and PHP's priority ordering), and `CallbackIdentity` is `_wp_filter_build_unique_id()`. Each function is a use case, a command or query, whose handler is registered in the service container. Its state is behind the outbound port `HookStore`: the four globals, read and written only through it. <Ev source="ss:crates/speedyspec-wp-hooks/src/store.rs#L12-L14" hash="8177cb03af5fe456b329ebda2a94732537263fbbd06a54bf4d6cc9cae0b4c518"/> <Ev scenario="add_during_run_at_later_priority"/> <Ev test="speedyspec-wp-hooks-php::php::replayed_scenarios_match_wordpress"/>

## Its adapters

- **Memory** (`speedyspec-wp-hooks-memory`): the store the runtime worker binds by default. <Ev source="ss:crates/speedyspec-php-runtime/src/worker.rs#L303-L307" hash="fbd4028d96f113c9616ae25ef31a11558260d2148ca7680c16506e632be0c1b8"/>
- **PHP** (`PhpHookStore`, in `speedyspec-wp-hooks-php`): a PHP object implementing `SpeedySpec\WpHooks\HookStorage`, the store port's twin, generated from the Rust trait by `#[php_port]` so the two can't drift. <Ev source="ss:crates/speedyspec-wp-hooks-php/src/stores.rs#L93-L93" hash="0c5e7de2e36720b9227a1c310497ba19922c675136437a4eac08a1ad97a45456"/> <Ev test="speedyspec-wp-hooks-php::php_store::php_hook_store_binding_takes_every_registration"/>
- **The PHP area** (`WpHooksArea`): declares WordPress's hook functions with their exact signatures, `WP_Hook`, and the proxies for the globals at the start of every request. Each is thin: a native function dispatches the use case. A PHP callback is one crossing into PHP; a hook with only Rust callbacks never enters PHP. <Ev test="speedyspec-wp-hooks-php::php::a_php_callback_is_one_crossing"/> <Ev test="speedyspec-wp-hooks-php::php::rust_caller_with_rust_callbacks_never_enters_php"/>

The store is bound in the container under `SpeedySpec\WpHooks\HookStore`. <Ev source="ss:crates/speedyspec-wp-hooks-php/src/stores.rs#L15-L15" hash="f74a671f2e70d8a1c4979dff0957c3b2508befdf433b7574eb856a13bbb27801"/>

## Patterns

- **Ports and Adapters** for the store: `HookStore`, with the memory and PHP adapters.
- **Command and query handlers** for each function, registered in the container (**Registry**).
- **Proxy** for three of the globals (`FilterGlobal` for `$wp_filter`, `CountGlobal` for `$wp_actions` and `$wp_filters`) and for `WP_Hook` objects, which are handles to Rust hooks. `$wp_current_filter` is a real array kept equal to the store's stack. <Ev source="ss:crates/speedyspec-wp-hooks-php/src/hooks.php#L118-L131" hash="d6926b1d27bda0cf7d16eb5967e975f9a793f3eb379e5fbedf268fcfd3b74098"/>

## How to change this

- **Keep hooks somewhere else:** write a `HookStore` adapter in Rust, or implement `SpeedySpec\WpHooks\HookStorage` in PHP, and bind it under the hook-store key.
- **What must still pass:** the recorded scenarios (`compat/hooks/scenarios.json`, replayed by `speedyspec-wp-hooks-php`'s tests) and WordPress's own hook tests run against the port, except the breaks listed in `compat/hooks/breaks.json`. <Ev test="speedyspec-wp-hooks-php::wordpress::wordpress_hook_tests_pass"/> <Ev test="speedyspec-wp-hooks-php::wordpress::documented_breaks_are_listed"/>
- **Recording a new scenario:** add it to `compat/hooks/scenarios.json` in speedyspec-server and run `cargo run -p speedyspec-compat -- record hooks --wordpress 7.1.5`; a difference the port can't match goes in `breaks.json` with its reason.
