## The domain and its port

`speedyspec-wp-hooks` is `plugin.php` and `WP_Hook` in Rust: `HookApi` holds every function, `WpHook` is `WP_Hook` ported literally (with how running iterations follow changes, and PHP's priority ordering), and `CallbackIdentity` is `_wp_filter_build_unique_id()`. Each function is a use case, a command or query, whose handler is registered in the service container. Its state is behind the outbound port `HookStore`: the four globals, read and written only through it. <Ev scenario="add_during_run_at_later_priority"/> <Ev test="speedyspec-wp-hooks-php::php::replayed_scenarios_match_wordpress"/>

## Its adapters

- **Memory** (`speedyspec-wp-hooks-memory`): the store the runtime worker binds by default.
- **PHP** (`PhpHookStore`, in `speedyspec-wp-hooks-php`): a PHP object implementing `SpeedySpec\WpHooks\HookStorage`, the store port's twin, generated from the Rust trait by `#[php_port]` so the two can't drift. <Ev test="speedyspec-wp-hooks-php::php_store::php_hook_store_binding_takes_every_registration"/>
- **The PHP area** (`WpHooksArea`): declares WordPress's hook functions with their exact signatures, `WP_Hook`, and the proxies for the globals at the start of every request. Each is thin: a native function dispatches the use case. A PHP callback is one crossing into PHP; a hook with only Rust callbacks never enters PHP. <Ev test="speedyspec-wp-hooks-php::php::a_php_callback_is_one_crossing"/> <Ev test="speedyspec-wp-hooks-php::php::rust_caller_with_rust_callbacks_never_enters_php"/>

The store is bound in the container under `SpeedySpec\WpHooks\HookStore`.

## Patterns

- **Ports and Adapters** for the store: `HookStore`, with the memory and PHP adapters.
- **Command and query handlers** for each function, registered in the container (**Registry**).
- **Proxy** for the globals (`FilterGlobal`, `CountGlobal`) and for `WP_Hook` objects, which are handles to Rust hooks.

## How to change this

- **Keep hooks somewhere else:** write a `HookStore` adapter in Rust, or implement `SpeedySpec\WpHooks\HookStorage` in PHP, and bind it under the hook-store key.
- **What must still pass:** the recorded scenarios (`compat/hooks/scenarios.json`, replayed by `speedyspec-wp-hooks-php`'s tests) and WordPress's own hook tests run against the port, except the breaks listed in `compat/hooks/breaks.json`. <Ev test="speedyspec-wp-hooks-php::wordpress::wordpress_hook_tests_pass"/> <Ev test="speedyspec-wp-hooks-php::wordpress::documented_breaks_are_listed"/>
- **Recording a new scenario:** add it to `compat/hooks/scenarios.json` in speedyspec-server and run `cargo run -p speedyspec-compat -- record hooks --wordpress 7.1.5`; a difference the port can't match goes in `breaks.json` with its reason.
