Partly ported in Rust, not in the runtime. Only the syntax pieces kses needs have a Rust port, in `speedyspec-wp-html-syntax`; no PHP area declares them and the runtime worker doesn't link the crate, so PHP code on SpeedySpec uses WordPress's own HTML API classes. <Ev source="ss:crates/speedyspec-php-runtime/Cargo.toml#L20-L55" hash="955f1ccec24cc11da3fa0826db96868561c6e6c3cdc55277b37b80c09b513508"/>

## What the port covers

The seam has 13 classes and 183 methods. The port covers five of `WP_HTML_Decoder`'s six static methods (`decode`, `decode_attribute`, `decode_text_node`, `read_character_reference` and `code_point_to_utf8_bytes`, as `code_point_to_utf8`), and the way `WP_HTML_Tag_Processor` reads a start tag's attributes, as kses's `wp_kses_hair()` uses it. <Ev source="ss:crates/speedyspec-wp-html-syntax/src/lib.rs#L1-L10" hash="ec3877330e3cd9435c09dc22da08e3161a9a16619536ef624055dc03c5b7c679"/> `WP_HTML_Decoder::attribute_starts_with()`, the Tag Processor, the HTML Processor and their supporting classes are not ported.

## The evidence

There is no compat area for the HTML API. The evidence is the crate's tests, which run the pinned release's own classes (WordPress 7.2-RC2) in PHP and compare:

- `decode()` in the attribute and data contexts, over subjects that include numeric references out of range, surrogates, C1 controls and named references with and without `;`. <Ev test="speedyspec-wp-html-syntax::decoder::decode_matches_php"/>
- every entry of the HTML5 named character reference table, and that the longest name wins. <Ev test="speedyspec-wp-html-syntax::decoder::table_matches_php"/> <Ev test="speedyspec-wp-html-syntax::decoder::named_references_take_the_longest"/>
- the attributes `WP_HTML_Tag_Processor` reports for a start tag, names and decoded values. <Ev test="speedyspec-wp-html-syntax::attributes::matches_php"/>

kses's own tests also run over these pieces (see the Formatting and kses seam). WordPress's HTML API PHPUnit tests are not run against the port.
